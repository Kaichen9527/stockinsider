## 1. One recommended storage/version decision

Retain **one existing storage family**: `research_input_preparations_v2` and `research_article_input_revisions_v2`, their immutable rows, unique `preparation_id`, foreign keys, source seals, original quota queries, owner/ACL and lock order. Keep `revision_kind='research_input_v2'` as this storage-family discriminator. Do **not** introduce a second ledger or a new revision-kind value solely for material wire-v3. Payload schema remains separately explicit and closed; retaining the kind is not permission to accept arbitrary new payloads.

Old sealed-v2 rows retain exact canonical_request, request_hash, canonical_payload, input_hash, logical_bytes, admitted_at/research_cutoff and source_seal_id. No UPDATE, backfill, clock rewrite, migration of rows or recalculated receipt. Resolve their **retained exact supported tuple**, not latest-by-symbol; if support is explicitly withdrawn, reject instead of falling back. Their read continues current source/head/rights, job/attempt/owner/reservation role, completion and original-lease fences. Read/replay does not open files, construct new material, charge or renew. The 120s preparation age applies to **new sealing**, not a new accidental 120s TTL on an already sealed row whose original lease remains valid.

Preparation remains deliberately **version-neutral**: existing eight-key request and exact immutable preparation payload; no invented job.financialVersion. Version/material tuple is frozen by the first successful complete ten-key request, uniquely bound to preparation_id. Two versions racing on one preparation cannot both succeed: global lock plus unique key and exact canonical_request replay comparison make the loser a conflict, never a second charge/revision. A caller requiring a different tuple after a seal needs legitimate new preparation capacity/lineage; no quota reset or automatic new claim. This is an explicit proposal to review, not an assertion that the original preparation already stored a version.

## 2. Finite requests and persisted shape

**Complete request remains exactly ten keys**, same scalar constraints and8192 bound: owner, jobId, attempt, reservationId, scope, snapshotHash, preparationId, preparationHash, expectedArtifactManifestHash, expectedCalculatorExecutionHash. Existing `parseCompleteRequest` is legacy15d4 `research-complete-input.ts:12`; duplicate-key/body parsing19. Symbol is never request-selected: derive from the live preparation/job lineage. Proposed tuple is `(parentSymbol, artifactInventoryHash, sourceExecutionHash) -> {wireVersion, financialProfile, financialSchemaIdentity, artifactRootId, compiledFingerprintIdentity, bindingCapsuleIdentity, freshExecutionState}`. Registry must be a finite **unique** relation; zero/multiple matches, unknown pair, cross-symbol, unsupported mode/schema or compiled mismatch reject before new preparation mutation or file I/O. Existing marker2 can remain the transport-envelope marker; payload wireVersion is inferred from the exact tuple, not a new request key. Do not silently accept marker3 or additional header semantics. This avoids conflicting marker meanings across four callers.

Preparation has eight keys (not ten): attempt,bundleId,jobId,owner,reservationId,scope,snapshotHash,sourceDocumentIds; bundleId=null, max30 unique UUIDs. A proposed versioned-preparation wrapper can take the two expected hashes as **separate typed RPC arguments**, validate parent-derived symbol/tuple first under the existing locks, then call original prepare. It does not change the eight-key persisted request or claim the neutral preparation has already frozen a tuple. Existing prepare stays callable for original fresh-v2; no flag silently disables it.

## 3. Source/compiled/DB binding DAG and complete known-input enumeration

Machine files enumerate actual `(subject,path,blob,bytes,SHA)` for known source inputs,135 statically resolved import edges,48 external package/builtin references, historical22file77b1 proof, actual SQL signatures/excerpts, and ordered50+26 installation inputs. The initial regex graph covers runtime controller seeds and literal imports (including type imports); generated-schema inputs and five `scripts/runtime` build-bridge files are added explicitly. No nonliteral loader was found in that bounded scan. **This is not an AST/build tracer proof of the future assembled application.** Dynamic Supabase RPC dispatch variants, fixed FS raw inventories, generated official modules, environment-selected server-client configuration, compiled Next chunks/NFT external files and runtime package resolution require separate final verification; they are not represented as magically zero dependencies.

Known candidate-overlay source graph prefers72f when a file exists, otherwise exact15d4. Historical22 rows are separately labelled even where the same path has different old bytes/lock. This is a design enumeration, not a claim the overlay has been assembled or tested. `absence-matrix.json` shows actual presence at72f/main1f/taildd. In particular the deep-job route, complete-input controller/mapping/bundles and author/reviewer/publication controllers are absent from72f/main1f; PR380 adds26 SQL and guarded installer/test code, **not** these app modules. Current71 subject/path records are not one approved whole closure. All original22 metadata hashes were recomputed to77b1; current9/7 and compatible8/6 are not substituted into that historical inventory.

Recommended DAG, with no self-hash trick:

1. **Execution source component S**: actual assembled route/auth/server client, common parser/controller, all four callers and supplement, downstream packet/article/review/publication validators, source/deep-context helpers, owner/engine/facades/pins/calculators/clocks, static raw/material schemas, original canonical/parser, finite registry **template** without its own digest, proposed protocol SQL **code/template**, existing contract SQL/profile/catalog references, root+web locks/package/config/.nvmrc and generated build-bridge inputs. Compute Hs over sorted exact metadata; graph/hasher code itself belongs to S. No fake-zero entries or arbitrary exclusions.
2. **Compiled component C**: exact normal build ID + complete server/NFT/package artifact manifest, Node/toolchain identities, actual compiled calculator/projector/validator fingerprint(s), generated modules and permitted nonsecret configuration digest. Compute Hc; do not reuse previous leaf/build as new compiled proof. Full build hash need not equal JS toString fingerprint. Functions used for new material must match the C binding; caller cannot provide this value.
3. **Binding capsule B**, generated only after S/C: finite two-symbol/version registry rows, exact artifact/schema identities and fixed-root IDs, Hs/Hc, final SQL mapping/registration data and final bound schema instance(s). Its own hash is not embedded inside its own bytes. Generated registration SQL that contains Hs cannot also be an input to Hs; it is a separately hashed child of the release DAG. Code/templates generating/verifying B are already in S; **B bytes remain pinned**, not an omitted untrusted initializer.
4. **Reviewed release envelope A** binds Hs,Hc,Hb, exact migration SQL/data profile and capsule verification contract. A is external authorization evidence, not claimed execution source. DB tuple activation and server loader must verify that exact A/B before use. The actual new hashes cannot be filled in this design; placeholders are symbolic names only, never zero hashes or approval booleans. A is not embedded in a schema/capsule that is hashed back into A.

Cycle consequence: a demand that one embedded `sourceClosureHash` literally hash every SQL/schema byte that itself embeds that same hash is impossible without a fixed-point trick. The necessary engineering revision is the explicit multi-component DAG above, not relabelling a leaf as whole. Hs alone is source execution identity; whole protocol approval requires S+C+B+A and deployment-state verification. The request expectedCalculatorExecutionHash selects Hs only through the approved unique B tuple; metadata alone never grants authority. Two bindings with the same selector but different version/schema must be rejected as ambiguous, not selected by date.

Original old mapping is retained solely for legacy validation; no editing its22file metadata or claims. Fresh compatible cutover must bind its new executed source/C and old8/6 artifacts. Release packaging must supply separate immutable fixed roots, not overwrite model paths. Archived original private-Set reader cannot run live concurrently with the new shared-owner realm; drain and deny new old-realm acquisitions is an explicit later operator transition, not silently changing fresh-v2 here.
