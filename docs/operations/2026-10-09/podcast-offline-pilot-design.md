## Budget, failure and cleanup

One heavy VM job, one monotonic1,800-second deadline INCLUDING network, resolution, installation, decode and ASR. Fresh startup and continuous free-reserve gate:8,589,934,592bytes. Task budget is4,000,000,000bytes, checked against both summed regular-file logical size and allocated blocks, including venv/wheels/model/audio/logs/outputs; RSS limit8,589,934,592bytes. A dedicated supervisor covers EVERY stage and samples free bytes, task allocation and the known process tree at intervals no greater than1second; record sample maximum rather than claiming a measured true peak. Each stage starts in an owned new Linux process group. Track PID/start-time identities and group descendants even after leader exit; success requires no remaining owned processes. On deadline or any resource breach, send TERM to the owned group, allow2seconds, send KILL to remaining owned identities/group, wait at most2seconds and confirm stopped; failure to confirm is cleanup uncertainty, never success. Do not reuse/delete a scratch root or launch the next heavy job while any process identity remains unresolved. These grace windows are explicit bounded failure handling beyond the1,800-second work deadline; no fresh stage may start then. If process supervision cannot cover these checks, report capability unavailable rather than running unmonitored. Stop before downloading if declared sizes cannot fit; observed values do not prove unobserved peaks. On failure preserve error/partial coverage and receipt, mark cleanup uncertainty explicitly if owned processes/file handles cannot be confirmed stopped; do not run another heavy job until resolved. Successful pilot does not authorize automatic deletion of unique evidence. Remove only explicitly enumerated reproducible wheel/cache/scratch paths after recording identities/hashes and confirming no process reference; retain private source/segment evidence needed for review until a retention decision. Lightweight preflight tests must exercise a stalled download, an over-budget writer, and a leader that exits while its descendant remains; demonstrate bounded termination, accurate failure attribution and no premature success/cleanup claim. Also test canary environment isolation and the no-index hashlocked final install arguments without downloading a model. No service, cron, credentials, formal strategy, database or production changes.

## Acceptance and interpretation

Actual bounded audio acquisition, verified wheel/model closure and executed CPU transcription are required for a content-capability success. A network refusal, missing wheel or timeout must name the failed stage. Segments are machine-generated, unverified text, not publisher transcript or confirmed facts. Financial tickers, company/person names, numbers and rumors need source/timecode confirmation before becoming evidence. No candidate scoring, EPS, author dispatch, publication or historical backtest signal is authorized by this pilot; any later excerpt admission needs separate reviewed content contract and retains the real first-observed clock. Report source-publication and ASR-execution clocks separately. Keep previous metadata_only receipts true and historical, even if this experiment later succeeds.
