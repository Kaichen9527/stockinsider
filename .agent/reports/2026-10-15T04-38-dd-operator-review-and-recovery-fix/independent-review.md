## R1 / P1 — Catchable termination can skip recovery after the pointer changes

Locations: lines89–92,110,160–162. Only `trap finish EXIT` is installed. Recovery is conditional on the incoming `$? != 0`; no TERM/HUP/INT handler records a nonzero interrupted outcome. A termination arriving after a successful command while `changed=true` need not supply a failure status to that EXIT handler.

An isolated exact `finish()` extraction with inert filesystem/service mocks demonstrated this: `changed=true; trap finish EXIT; kill -TERM "$$"` terminated by signal15, ran the cleanup diagnostic, but **never invoked pointer restoration, old activation, writer confirmation or service confirmation**. A normal `exit 42` positive control invoked all those mocks and retained exit42. No actual deployment or production commands were run. This is more precise than saying EXIT is never called: in this observed Bash case EXIT did run, but its recovery branch was skipped.

If this occurs after line161, `current` can remain DD while the writer/environment/services are still old or partially activated. Atomic symlink replacement alone does not repair the multi-component transition. Request: explicitly handle supported catchable signals, retain a nonzero failure/interruption status, make recovery non-reentrant, and define settlement of an in-flight activation child before competing rollback mutations. Verify interruption at pointer/activation stages with a safe harness. SIGKILL/power loss cannot be solved by shell traps and need an explicit uncertain-state/manual reconciliation boundary; do not promise universal signal recovery.
