## Decisions and actual blockers

The new full material fits the existing per-material and projection caps in an actual PostgreSQL 17.11 canonical measurement, but does not satisfy the old v2 finite schema. A versioned schema/registry and every downstream consumer need explicit dispatch. Merely wrapping the HTTP route is insufficient. The existing old artifacts remain reconstructible: every original AUO 8 / EMC 6 inventory member matches Git `75d91024ce365606989bfe42b2d7e6227b65044d`. At 15d4 the two model paths have been replaced by cash successors and fail the old inventory pins; the other twelve files still match. Do not substitute those new models in fresh-v2.

The legacy 22-file metadata closure was independently rehashed against Git: `77b1cc06b12d45063af75e976605fb9c4725da60f2c58bd39b28d54028590a41`. The leaf 14-file `f28549ba9d63ff909e3470a144793d5ca4940491822f38684a65f126d4d54624` does not cover an HTTP/PG execution closure. Neither identifies a new shared-engine execution as old 77b1. Original inventories pin old model sizes 88790 (2409) and 54602 (2383), not the new model sizes.

Two decisions are required before activation: (1) explicitly cut fresh-v2 callers to a newly approved compatible execution tuple while preserving old sealed replay and draining old fresh work, or retain the immutable old execution realm with a genuinely shared cross-realm resource coordinator; (2) select and approve the exact v3 request/schema/RPC tuple and full closure. ## Minimal storage/RPC amendment proposal

Reuse the existing immutable preparation and input-revision ledgers: the current revision table has no schema-version CHECK and has a unique preparation_id and existing downstream FKs. This avoids a new parallel quota ledger. The new strict v3 parent/read/seal functions should bind an explicit registry tuple, retain source→global→row lock order and recheck clocks after waiting. V2 public signatures and their old canonical bytes remain supported. If a v3 request adds version/profile keys, its new parent builds a separately validated legacy lineage subset for the original preparation assertion, while preserving the full v3 canonical request for revision replay; never rewrite an old row/request. Exact v3 request format remains a design decision, not deployed SQL.

One preparation may create one immutable revision only. A second version cannot reseal that same preparation due to the unique key; select the version before that operation. New attempts/jobs/reservations use the existing admitted workflow, not synthetic author/reviewer IDs. No second reservation solely to evade a spent byte/count budget. Expired/deleted/taken-over work does not refund retained charges. If a separate v3 table is chosen instead, every v2/v3 admission query must be amended atomically to include it; without that change the quota is bypassable, so this report recommends the existing ledger.
