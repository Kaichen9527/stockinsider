# T09｜行事曆同步的官方停牌收據

在原本的官方行事曆同步完成後，啟用強勢發動雷達的環境會以既有內部 operator 身分送出一次收據收集動作。動作只接受名稱，由受信任的伺服器抓取固定證交所 CSV、櫃買中心 JSON。既有 writer release、來源授權與租約皆有效，且該市場的台北上午或下午時段尚無收據時，才發出請求。每一成功時段保留實際錄入時間，原文依雜湊共用儲存。

盤後循環依榜單 cutoff 讀取當時可知的最新收據。確有開盤停牌時寫入無法成交，並綁定原本的次一市場交易日。資料集移動到其他事件時，可保留同訊號先前已確認且尚未被改正的開盤結果。收到同日不一致公告時保留開盤證據不足；已記錄這類更正的較新版本不會重新採用舊停牌報告。原始資料和內部收據不進入公開回應。

收據收集失敗不使既有行事曆同步失敗。此提交沿用原同步 script 步驟，既有 systemd timers 沒有修改，也沒有新 queue 或模型操作。開盤撮合的成交正例、真實排程端到端與發布 gates 仍待驗收。正式服務沒有變更。

## 驗證

- Contabo 隔離 PostgreSQL 17.11 驗證同時段重送、內容去重、雜湊、截止前可知、匿名拒絕、既有收據保留、更正不回退，以及來源授權有效期。
- 53 個 Node.js 測試和相關檔案的嚴格 TypeScript 5.9.3 檢查通過。包括真正的行事曆 script 在相同流程、停用及交易所來源暫缺時的執行測試。SQL 及檔案雜湊與整合分支核對。
- 真正的 Node 收集器從兩個交易所讀取公開資料並檢查 MIME、位元組大小及雜湊。以模擬寫入介面收集去敏中繼資料，沒有將這次資料寫入正式或 staging 資料庫。〔[證交所資料](https://data.gov.tw/dataset/11677) · [櫃買中心資料](https://data.gov.tw/dataset/48665)〕
