# Durable complete research input v2 — proposed narrow contract

Status: PROPOSED; no requirements approval, implementation, deployment or model authority is supplied by this document. Design source is ceafb7b919b545fa37c3d6f1372920c83bd08a95 (tree8d8dc64bbcf558c57caded823261052ae4d4db8a). Financial dependency is the reviewed-design candidate a2046447a74d98f78c51fef5162c8bf571371370, especially financial-adapter-slice.md and its finite file inventory. The financial implementation is concurrent work and must receive its own exact-source review; this proposal does not assume that design is implemented. The first-publication-v2 parent requirements remain controlling.

## 1. Outcome and boundaries

A supported observed research job can assemble, atomically persist and subsequently reread its first immutable `research_article_input_revisions_v2` row without an already published formal stage. The row refers to its original immutable preparation; it never rewrites that preparation or turns the existing read-only financial supplement into a receipt retroactively. It retains enough typed material and distinct identities for the subsequent existing dossier/bundle/outbox/submission/review flow. No second publication system is introduced in this slice.

`assemblyStatus:'complete'` means the closed input package has been durably assembled with every required section and explicit unavailable values. It does not mean all evidence or forecasts are complete. `evidenceStatus:'incomplete'`, named financial/source gaps, `financialVerified:false`, `dispatchReady:false`, `modelDispatched:false`, `publishableResearch:false`, `researchQualified:false`, `strategyApproved:false`, `entryEligible:false`, and `historicalPITEligible:false` are fixed in this slice. Null/missing sections are not accepted as a complete assembly. Unavailable annual bridges, commercial operating assumptions, citation locations or verification authority remain typed gaps; no fabricated numbers, locations or approved flags fill them. A later author/review capability must consume this exact hash through an independently reviewed versioned input union and satisfy remaining gates. This slice creates neither an article nor a completed deep job.

This interpretation of complete assembly versus complete evidence is an explicit requirement to review, not a silent weakening of first-publication-v2. A package that cannot identify its financial company, finite artifact inventory, reported-versus-assumed operands and exact fixed calculator must be rejected, not sealed under the word complete. Unsupported symbols retain the existing unavailable supplement and cannot create this revision. Initially only2409/AUO and2383/EMC are supported; no substitution for5347/6531 or another claimed company.

## 2. Closed ingress and trusted boundaries

Use POST on the existing `/api/internal/research-deep-job`, adding only `action:'sealResearchInput'` and `action:'readResearchInputRevision'`. Authenticate first with existing `requireExactInternalBearer`, which delegates to requireInternalAuth and excludes cron/review/test/strategy keys and x-internal-key. No GET, public download or client-supplied artifact body. For these new actions, bound actual body stream to8192 UTF-8 bytes (Content-Length alone insufficient); reject invalid UTF-8, duplicate JSON keys, extra keys, nulls and wrong types. Do not change existing formal/default actions.

Both actions accept exactly action, owner, jobId, attempt, reservationId, scope, snapshotHash, preparationId, preparationHash, expectedArtifactManifestHash and expectedCalculatorExecutionHash. UUIDs/hashes and original attempt1..3 follow existing lower-case closed types; scope is exactly research_observed_v1. The request selects neither paths, source IDs, source contents, financial values, model code/output, clocks, qualification, author/reviewer identities nor transaction policy. Preparation determines selected source IDs and company. Hash expectations are compare-only constraints against the finite reviewed server mapping, not caller authority. The read action returns only an already persisted exact revision or an explicit absent/fenced result; it never computes or writes. The seal action performs the same bounded lookup first, and calculates only if absent.

Proposed SQL signatures are `read_research_article_input_revision_v2(p_request jsonb) RETURNS jsonb` and `seal_research_article_input_revision_v2(p_request jsonb,p_calculation jsonb) RETURNS jsonb`. The internal p_request omits only action; the remaining shape is identical for read, write and replay identity. p_calculation is built by the server adapter, never copied from HTTP; it has a closed versioned schema reviewed with the financial implementation, maximum262144 UTF-8 bytes, maximum64 facts,3 scenarios×6 quarters, depth12 and fixed company fields. The DB repeats shape, company/parent, numeric/domain, locator, provenance, chronology, inventory, hash and quota checks; unknown nested fields reject. The final per-field schema and canonical cross-language vectors must be frozen before code review, not accepted as arbitrary JSON. The parent financial design's file/read/projection/output bounds continue to apply.

These are ordinary guarded storage RPCs, not cryptographic signatures, independent execution evidence or proof of honest service-role code. Existing service_role can invoke allowed RPCs; compromised service-role credentials are outside a claim of independent verification. The database can bind the submitted calculation to the reviewed static manifest and transitive calculator digest, but a digest does not prove execution. The row records `producerAttribution:'internal_controller_asserted'` and actual artifact-byte verification separately; no new trusted principal, signing key or registry is created. An unknown author/reviewer/provider identity remains unavailable. Future authenticated role execution must independently prove its authority and exact input, not treat this storage receipt as its signature.

## 3. Durable row and separate hashes

One new private append-only table; no new financial raw store or new publication table. Mandatory relational fields: revision_id UUID, preparation_id UNIQUE FK, job_id/attempt/reservation_id matching that preparation, research_company_id, original research scope/snapshot, request_hash, canonical_request, input_hash, canonical_payload JSONB, logical_bytes, admitted_at, research_cutoff, source_seal_id nullable only when the preparation had no selected sources. Immutable UPDATE/DELETE/TRUNCATE rejection includes table owner paths. No mutation of source, stocks, instrument authority, strategies, stages, budgets, claims or completion rows is exposed.

The closed payload contains schemaVersion, assembly/evidence status, parent preparation ID/hash, DB-derived researchCompanyId/symbol/snapshot/member/mappingDigest/optional existing stockId, priority run/input/discovery cutoff, original job/attempt/owner/reservation/deadlines, original source seal+manifest, typed financial observations and assumptions, calculation envelope, source-coverage/rights/verification gaps, originalModelCutoff, original observation/recorded clocks, artifactReadKnownAt, financialAdmittedAt, researchCutoff and fixed false capabilities. It includes no private raw PDF/sourceNumericLines, credential, local absolute path or arbitrary user string. Private fixed inventory identifiers/relative allowlisted paths may identify evidence, never select a file at runtime.

Separate identities must not be conflated: (a) original preparation input hash, (b) complete artifact byte inventory hash with each SHA256/length, (c) old model historical canonical hash, (d) full source-manifest canonical hash, (e) projected factual/assumption-input hash, (f) actual transitive calculator/build execution identity, (g) recalculated result hash, (h) final DB canonical input hash. Hashes are SHA256 over explicitly versioned canonical UTF-8 encodings. DB derives request and full input hashes; it recomputes every subhash whose bytes are present rather than trusting the supplied hash. Financial implementation must define safe numeric canonicalization (including no nonfinite/-0 ambiguities) and cross-JS/PG Unicode/number vectors. DB source row hashes retain the existing PG source-fence encoding and are not relabeled as these canonical hashes. No generic JSON.stringify hash substitutes for the established per-schema rules.

Financial fact records retain metric, exact period/kind, unit/currency/sign convention, typed reported/derived/assumption status, operand locators, immutable artifact byte identity, JSON pointer, real PDF page/column when known, acquisition and relay attribution, source observation/recorded clocks, publication precision and verification limitation. A reported label describes attributed provenance, not VM independent PDF verification. Rounded EPS subtraction is prohibited; forecast and PE assumptions are not source facts. Preserve the AUO/EMC distinctions and unavailable YTD bridge from the financial design. Derived facts name typed operands; unknown locations are explicit gaps, never invented source_raw_documents IDs.

## 4. Admission, source rights and PIT

The preparation and old read-only supplement remain unchanged. Actual new financial admission is `clock_timestamp()` sampled inside the locked insertion transaction after validation, immediately before generating the payload/hash/row. This DB timestamp is financialAdmittedAt and researchCutoff; the row admitted_at equals it. A DB admission timestamp is not a commit timestamp. Client clocks, request start and old preparation cutoff cannot supply the new cutoff. DB rejects nonfinite/future source/artifactReadKnownAt clocks, microsecond inversions, and originalModelCutoff inconsistent with the exact fixed artifact. Original artifact and relay observations remain distinct, including EMC notes recorded after its raw PDF read. Date-only/unknown publication stays typed date/unknown; it is not promoted to midnight or an exact publication instant. Old model cutoff remains visible even when newly admitted material was unavailable then. The package is current research only.

Under the stable source fence, assert the preparation's exact source seal and all stored row hashes/current heads/rights/invalidation history. Reuse that seal; do not acquire a new cutoff merely to refresh it. Null seal is legal only for an originally empty source selection, with explicit source_selection_incomplete. No new source selection is accepted by the complete-input request. A changed selection requires a new charged preparation. Root/parent-repost limitations in the source sealer remain; this slice does not implement ancestor permission inference.

The finite financial artifact inventory is a different evidence namespace from source_raw_documents. Its reviewed bytes/locators and honest relay attribution may be stored as private research input, but do not automatically inherit public_citation, source-fence coverage or current rights. Missing mapped source lineage/withdrawal authority is retained as `financial_source_live_rights_unverified` and blocks downstream publication/dispatch readiness. A controller may not invent a source row or claim the local git manifest observes external withdrawal. Existing source-backed citations retain their exact DB seal; financial artifact assertions without that linkage remain private/unverified. For each new seal and live reread/replay the server must confirm the exact original static inventory is still in its reviewed supported mapping; a new code/artifact version is not an implicit reapproval of an older one. Future publication needs actual rights/withdrawal integration and independent financial/citation review. These are explicit downstream prerequisites, not reasons to deny bounded private storage of an accurately attributed assembled input.

## 5. Original lease, replay and atomic persistence

READ COMMITTED only, rejected before replay/locks/writes. Order remains source advisory610091002 → existing global deep/model advisory(2409,6002) → original job/reservation row locks → quota/immutable rows. DB rechecks the original running observed job, exact owner/attempt/snapshot/priority-store/member lineage, matching company_research reservation and `deep:<jobId>:<attempt>`, original attempt receipt, finite start/deadline, no completion and no expired lease after lock acquisition. Do not accept a different active reservation or merely any live production lease. This slice is not a deployment/backend-lease fence and must not claim the existing prepare RPC supplies one. Future production rollout still uses the separately reviewed data-plane deployment and ownership controls.

New admission additionally requires original preparation admission no more than120 seconds old at final locked check and finite current server time. The controller shares one10000ms monotonic deadline across initial live read, finite artifact reads/reexecution/serialization, final RPC and response validation. Every async operation receives remaining-time abort/timeout; DB statement/lock timeout must be bounded by remaining budget. No locks span filesystem calculation. After work, SQL rereads source/lease fences and samples real admission; it checks deadline again immediately before insert/return. Expiry after a transaction committed cannot erase the row; it prevents later usable reads and is never a fresh lease. Unknown HTTP commit outcome is recovered only by the exact read/replay, never a new claim or automatic retry with changed clocks.

Replay key is the complete canonical request (without action), scoped to original unit; one revision per preparation. Read-only lookup validates current original lease, lineage, source seal and supported immutable mapping before returning the original stored payload/hash/clocks. If absent it returns absent, not a manufactured revision. Same preparation with different request/expectation rejects conflict. Exact replay can succeed at exhausted quota and after the original120-second preparation admission window, because no new material is admitted; it cannot change the original revision timestamp or grant refreshed120-second dispatch freshness. Any future dispatch freshness uses original revision admitted_at. Replay after lease expiry, source invalidation, completion or removed supported mapping rejects; permanent history remains private for later authorized audit. Replay does not rerun the calculator with fresh knownAt and silently compare it to old evidence.

Write transaction repeats all read checks, validates complete material, checks shared quota, assembles and inserts the row atomically. Losing concurrency returns the same exact persisted revision if request identical, otherwise conflict; it must never overwrite first evidence. Insert, any associated receipt fields and accounting commit together. This slice needs no new source seal and no extra accounting journal: logical_bytes stored on the immutable row is the durable charge. All failures roll back completely. Existing reservations retain original30-minute/day/week charges; no reservation, extension, completion, refund or retry attempt is created by sealing.

## 6. Shared nonrefundable quota and privileges

Both old `prepare_research_input_v2` and new sealing RPC must count the UNION ALL of preparation rows and complete revision rows for the exact original(job,attempt,reservation). Combined count≤4 and combined cumulative canonical UTF-8 bytes≤524288. This is one shared cap, not4+4 or two524288 allowances. Existing preparation logical_bytes retain their value, including originally charged new source seals. New row charges full canonical internal request plus full canonical payload; the payload includes the complete calculation and stored source manifest. Any newly persisted duplicate JSON/receipt material must be included or excluded by schema design before review, never silently free. Fixed relational indexes/columns are physical overhead, not represented as a measured physical cap.

Original preparation rows count permanently. A preparation+its completion consumes two slots; two such pairs fill four. Four historical preparations leave no slot for completion and correctly reject: no deletion/relabeling/refund. Read-only supplement remains free of durable writes; orchestration should attempt completion after its first preparation. Expiry, source invalidation and failed takeover never free charges. Additive migration must replace only the old preparation admission query to include the new table under the same existing lock. Merely adding a new RPC check would let the old RPC bypass the combined cap. Do not edit the historical migration file. Migration preflight checks exact predecessor function definition/owner and reviewed plan hash; a divergent installed body fails closed, not blindly overwritten. Existing immutable receipts are not rewritten or backfilled as complete.

RLS enabled; private NOLOGIN NOSUPERUSER NOBYPASSRLS owner with explicit table/function SELECT/EXECUTE grants and minimum row-lock privileges only. Reuse the preparation owner if its finite privileges suffice, otherwise the exact additive owner/grants must be independently reviewed. No direct SELECT/INSERT/UPDATE/DELETE/TRUNCATE to PUBLIC, anon, authenticated or service_role on new table; only closed read/seal RPC execution to service_role. An unprivileged SQL fixture must test actual policies, not only superuser SET ROLE success. The owner cannot modify protected job/reservation rows through its lock grants. Old prepare helper needs explicit read permission/policy for new immutable rows. No public raw/evidence exposure or new owner membership.

The cap is logical per original unit, not a global VPS4GB source-evidence or disk/WAL guarantee. Retained history grows with legitimate jobs; rollout requires existing shared storage/host guards and measured overhead. No new archive/deletion/cancellation policy is granted. 5 weekly companies×3 attempts×524288 is at most7.5MiB logical input charge per fully new weekly cohort when those existing admission limits actually apply; this is not a bound on all pipeline writes, jobs from other scopes, raw originals, physical indexes or WAL.

Retain original budget and no extra model claim on every failure.

Unlinked financial artifact rights remain unverified even when its hashes match.
