## 1. Problem and scope

V1 counts all retained raw and completed snapshots against128MiB/32 records, with lifetime128 runs/640 mappings. Five fresh datasets each day can complete at most six cycles from an empty store; the seventh needs35 slots. Five maximum payloads require60MiB reserved before acquisition. Finishing a page releases only the per-dataset active restriction. Repeated identical responses are distinct observations and do not currently deduplicate storage. This is intentional finite V1 behavior, not failed V1 acceptance.

V2 proposes moving ONLY completed insider snapshot raw payloads from hot SQL storage into the existing persistent private artifact store. It preserves byte-identical recovery, acquisition identities and document/CAS lineage. It is not generic data cleanup: financial statements, original research documents, existing private artifacts, source documents, database history, other Apps and their backups cannot be deleted or rewritten. No new database, public API, provider, bucket, paid service, model authority or official-source procurement is introduced. Existing default/symbol collection paths and schedules remain unchanged until separately reviewed rollout.

A VPS-local archive is still VPS storage. Compression/deduplication can reduce physical cost; it cannot promise indefinite history within4GB or make an ephemeral Cloud workspace durable. Moving the only authoritative archive off VPS is outside this slice. Existing encrypted backup may provide another copy only after its exact format/restore compatibility is demonstrated; successful export is not proof of restorable storage.

## 2. Evidence identity and physical storage

Keep each snapshot UUID, dataset, original raw SHA256/byte length/row count, attempted_at, observed_at, admitted_at, parser/rights identity forever in the authoritative DB. Keep every source document ID/URL/content/hash/metadata and first collected_at, run/member/token identities, final offset/generation/completed_at and durable completion/CAS receipts. Archive and restore clocks are new operational fields; neither replaces source clocks, publishedAt precision, source freshness or the first document storage time.

Physical deduplication is permitted across acquisitions only when the exact original raw bytes match (hash AND byte length, verified readback). Different dataset/rights/parser/observation identities remain separate immutable records, even when they reference one physical artifact. No JSON reserialization, normalized whitespace, sorting, re-encoding or field removal may stand in for the original bytes. No document URL/hash is reissued because physical storage moved. A new live acquisition of unchanged bytes is a new observation; replay of an old acquisition is not.

Reuse `privateArtifactStore` under the deployment's existing private artifact root. Caller input never supplies a filesystem path, host or arbitrary artifact hash. The archive adapter derives content from the locked DB snapshot and a closed encoding profile. The bounded profile is either identity bytes or a single gzip member; no tar/zip paths, concatenated members, trailing data or unknown codec. Store the exact encoded-object SHA256/length, codec/version and raw SHA256/length in an immutable DB artifact-binding receipt. Raw output remains2..12MiB and at most50,000 rows; encoded input is at most12MiB+128KiB. Gzip decoding must stream with both the declared raw-length and12MiB output limits, abort/deadline and finite working-memory bounds; validate full stream termination/checksum and exact raw SHA256 before exposing bytes. Compression bombs, truncated streams, extra members and byte/hash mismatches fail closed. Byte-hash verification occurs before any parsing, followed by the original parser/rights/schema checks where the reader needs evidence content.

Use identity encoding when compression would exceed its input bound. Existing verified storage for the same raw content may be reused even if a newer compressor would emit different bytes; do not overwrite old artifacts or require compressor-version determinism. Private permissions, no-follow regular-descriptor verification, bounded reads including a growth sentinel, no-overwrite publication, file/directory fsync and readback are mandatory. FIFO/device/symlink/rename/growth races must refuse or remain bounded. A filesystem path or caller-supplied hash alone is never an archival receipt.

The current generic receipt schema accepts only financial_document/diagnostic_attachment. Do not mislabel raw archive as diagnostic data or reuse a foreign purpose's receipt. Add a reviewed explicit insider archive purpose/binding with existing backend lease ownership; preserve prior purposes/receipts. Exact duplicate physical objects can have separate authorized purpose bindings without mutating an existing financial receipt.

## 3. Proposed state transitions and authority

Only an existing `requireInternalAuth()`-guarded internal source operation, with the established production-data-plane/write lease, may request bounded maintenance. Its closed request selects a completed snapshot UUID; it cannot specify bytes, clocks, destination or trusted completion claims. The trusted backend reads and verifies the actual private store. SQL cannot attest filesystem durability on its own; a generic service-role receipt insert or a client-supplied digest cannot authorize raw eviction. New private tables/routines use RLS/revocation and an explicit exact backend/lease/attempt fence described below; the existing generic backend check alone is insufficient. No anonymous/authenticated direct access, arbitrary SQL owner, new credential or second ingestion route is introduced.

### Exact backend, lease owner and attempt fence

The existing `assert_stockinsider_backend_request_v1(true)` is not sufficient archival authority: it can accept the existence of another owner's live production-data-plane lease, and a disabled identity fence may return NULL. V2 MUST reject NULL/disabled/unresolved backend identity and independently verify the exact active registered backend identity, production-data-plane lease identity/owner and expiration for THIS operation. A general INTERNAL bearer, service_role or some other live lease is not equivalent evidence. These values come from the authenticated route/backend context, not request JSON; the public action still accepts only snapshotId. If the deployed route cannot resolve an authenticated backend and its exact owned lease, archival mutation fails closed rather than inventing an identity.

Every durable operation records immutable snapshot/raw binding plus a monotonic attempt/fencing generation. Each attempt records authenticated backend ID, exact lease ID/owner, start and verification receipt identity. Reserve, verification registration and finalize all compare that tuple with trusted request context and the locked current operation. In the final transaction lock the exact backend/lease rows and current operation along the reviewed shared order, recheck backend enabled/registered identity, exact lease owner/ID/generation and expiry against server clock after acquiring locks and immediately before mutation. No caller-selected tuple or old verification receipt can satisfy the current attempt. Concurrent lease transfer must serialize against these locks; merely checking a lease before file I/O is insufficient.

Restart under the same still-valid owner may inspect/reconcile the same operation; it must reopen and reverify the final artifact before a new finalize request. If the original lease expired or was verifiably revoked, an authenticated new owner may take over ONLY by explicit compare-and-swap against the prior operation attempt, preserving the operation ID, snapshot/content identity, quota reservation and immutable old attempt history. The CAS installs the new exact backend/lease tuple and increments the fencing generation. No live owner is silently preempted. New owner B must perform fresh bounded artifact reopen/decode/hash verification bound to B's new attempt. A's old verification cannot finalize under B's lease, even when object hash is unchanged. Late A reserve/verify/finalize requests reject without releasing reservations or changing hot/archive state. Lease loss during verification leaves hot raw and durable reservation intact for this explicit reconciliation; it never activates automatic retry or capacity release.

The proposed existing-route request is `POST /api/internal/source-sync` with exactly `{ "connector": "twse_insider", "insiderArchive": { "snapshotId": "<UUID>" } }`. It is mutually exclusive with normal acquisition/pins/symbol options. Return a closed private operational receipt (schema, operationId, snapshotId, storageState and safe reason); expose no raw/path/person fields. Only a verified archived or exact replay result may be200. Queued/capacity/unavailable is a distinct non-success503, auth failures keep existing401/403, malformed requests400, identity/state conflicts409. It must never produce the continuation controller's typed `pages_remaining`502 or update live acquisition/source succeededAt. Reuse the route's existing authentication/write-lease ownership while keeping archive maintenance out of source collection/health-success accounting. Deployment-specific policy may disable this opt-in action entirely.

Use an additive storage-location/state relation and operation journal. Preserve V1 immutable identity columns. The additive migration may make V1 raw nullable ONLY behind the reviewed hot→archived transition; no direct DELETE of snapshot identities and no broad removal of the immutable trigger. Legacy raw rows remain hot until individually archived. The exact migration must preserve installed ownership, ACL and predecessor compatibility and be independently reviewed before use.

1. **Reserve:** under the exact backend/lease/operation fence and existing global capacity→dataset lock order, verify complete progress, exact immutable snapshot/terminal receipt and absence of unresolved writes. Record one durable archive operation bound to snapshot+raw identity and reserve worst-case artifact/staging/quota usage. Claim/replay returns the original operation. Shared-content publication has one durable object reservation across concurrent snapshots, not two unrecorded free-space assumptions. Release DB locks before file I/O; reservation remains charged.
2. **Publish:** read the original bounded hot bytes, independently recompute identity, encode, create-only publish to the existing private root, fsync file and directory, reopen and decode/hash-verify the final object. Record its immutable artifact/purpose and verification binding including the current backend/lease/operation-attempt tuple; reject if that tuple lost ownership. Failure leaves hot bytes and all operational reservations intact; no false archived state. A pending file or orphan object is not success. Resume reconciles the original operation/object; no new identity, automatic expiry or unaccounted second allocation.
3. **Commit archive:** with the same lock order, locked exact backend/lease rows and current operation attempt, recheck the exact operation, completed snapshot, artifact binding and verified object; atomically append the location/completion receipt, clear ONLY that snapshot's hot raw, mark archived, release its hot-byte/hot-slot charge, and exchange archive reservation for actual charged storage. All snapshot evidence identities, documents, run/token bindings and original clocks remain. If the DB commit outcome is uncertain, query the operation first. Never delete the archive or attempt a second eviction to guess the result.
4. **Replay/read:** V2 readers resolve by existing snapshot identity, never by a client path. Hot rows use original verification. Archived rows require actual artifact retrieval/decode/hash and parser/rights validation before returning evidence or a completed page/replay receipt. Unavailable/corrupt/wrong-rights archive yields a typed unavailable failure, not successful-empty, completed HTTP200, renewed freshness or a new live acquisition. An old valid page CAS retry returns only its already committed receipt; mismatched span/generation is rejected. Archived incomplete snapshots are invalid. Original completed documents and history remain queryable, with an explicit unavailable-raw status when relevant; a general document reader cannot claim raw revalidation that it did not perform.
5. **Recovery:** restore at most one raw object into a bounded private memory/staging buffer for read verification. Do not permanently rehydrate every historical raw into the128MiB hot budget. Any future durable rehydration requires an explicit reserved hot transition. Crash/restart preserves the exact operation and receipts, with no event that invents source acquisition or extends a source deadline.

DB and filesystem are not a distributed atomic transaction. Safety comes from publish+verify before DB eviction, private immutable artifact access and durable reconciliation. Same-UID/root compromise, hardware durability and independent backup restore are separate operational boundaries; neither a hash nor fsync proves them away. If the persistent store cannot provide the required ownership/restore contract, refuse hot eviction.

## 4. Capacity and lifecycle accounting

Preserve the128MiB operational hot+pending-raw byte cap and32 operational hot-snapshot+pending-token slots. Completed snapshots count as hot until their archive commit succeeds. A pending acquisition still reserves12MiB and one slot, shared once per dataset. Archive I/O and failure never release acquisition liabilities. Existing frozen runs continue at new-admission limits.

The128-run/640-member limits become bounds on **operational unfinished runs and their five members**, not lifetime history. A fully completed run may leave the operational set only after its five terminal receipts and immutable mappings are durably present; those rows stay in historical lookup and are never recycled. Historical snapshot/run/token/member/receipt records are indexed and keyset-read in bounded pages (maximum500); no unbounded history scan in begin/read/commit. Every retained historical byte remains subject to the source-evidence/project storage budget. This is not an unlimited metadata exemption or silently increased integer cap.

Use the user-required VPS source-evidence engineering budget of **4,000,000,000 bytes**, distinct from4GiB. It is shared with protected original source evidence, not a new4GB allowance just for insider archives. Count retained private evidence objects (shared objects once), charged hot SQL evidence, historical metadata/documents/index allocation, durable reservations, unverified/orphan publications and peak temporary copies conservatively. Archive publication must not double-count a shared final inode as two objects, nor hide its temporary bytes. Copying raw from DB to the same VPS store is not reclaimed filesystem space until actual allocation measurements prove it; SQL tuple/TOAST/WAL reclamation is not immediate. No automatic VACUUM FULL, destructive rebuild or backup deletion is authorized.

The shared invariant is `measured charged allocation A + all outstanding durable reservations R + requested peak delta Δ <= 4,000,000,000`. For archival publication, Δ includes at least maximum encoded bytes (12MiB+128KiB), one raw-sized restore/staging allowance, and the reviewed DB/index/WAL metadata headroom; an existing verified content object removes only its already charged final-object component, not temporary verification headroom. Reserved deltas exchange for reconciled actual allocation only after commit/cleanup is confirmed. Content-addressed `.pending`/orphan files remain counted after crash. The implementation must select a versioned finite conservative metadata/WAL reservation profile from actual PG boundary measurements and bound each batch accordingly; an unmeasured or underestimated profile fails admission rather than pretending Δ is zero. This profile and all shared-writer participation are required design inputs, not optional production tuning.

New acquisition, archival publication and restored reads all check the shared budget under coordinated existing resource/backend locks, retain durable reservations across requests, and recheck real allocation/free space before irreversible transitions. Require measured peak allowance for compression, temporary copies, database/index growth and WAL; an unavailable measurement or unsupported concurrent-writer accounting queues the operation. A checked-at-start free-space estimate alone is insufficient. The proposed per-operation implementation must specify and test conservative reservation formulas before implementation review; it cannot claim a hard physical bound from a raw-length-only counter. Existing other-source writers must participate in the shared admission contract before production activation; otherwise this feature stays opt-in/unactivated.

Respect the existing whole-host guards in addition to the4GB evidence budget. VM acceptance remains one heavy job,20GB resident/4GB temporary/8GB reserve with measured aggregate usage; production must use the installed stricter VPS guards, not substitute VM free-space numbers or filesystem availability for project quota. Guard refusal means a bounded queue/capacity reason, preserving all necessary evidence. No cleanup of other Apps, financial/research originals or required backups. No auto-expiration, archive retention deadline, source-evidence pruning or indefinite-daily-operation claim is introduced.

Failed pending-acquisition cancellation/abandonment remains a separate amendment. There is no token TTL, cancellation RPC, forged empty snapshot, deletion/reuse of consumed token or silent release of a partially acquired set in V2. Permanent source failure can continue to reserve capacity; expose it separately from completed archive backlog.

## Component progress — first isolated slice

The codec candidate implements the closed binding, exact raw/encoded bounds, single-member streaming gzip decode, CRC/trailer/SHA256 verification and byte-identical restore. The private-I/O candidate reuses the unchanged privateArtifactStore in a fresh private staging directory, publishes a create-only hard link in the existing hash layout, then checks actual file/directory descriptors, fsync and readback. Its return explicitly contains evictionAuthorized:false. It has no DB receipt, backend/lease identity, reservation, hot-raw deletion, parser/rights reader or public entrypoint. Synthetic bytes only were used.

Decode has a finite 30-second timer, abort and per-chunk checks; its promise settles after the zlib stream closes. Filesystem operations have monotonic deadline/abort checkpoints around bounded regular-file reads and publication. They do not provide forced cancellation of an already pending kernel open/fsync or the reused private-store call. A filesystem/kernel stall is therefore not yet a proven end-to-end operation deadline. Failure staging is retained for later explicit reconciliation, never silently deleted to recover quota; its future allocation must be included by the shared reservation protocol.

A caller-selected temporary test root is not proof of the deployed persistent root, backup compatibility, host guard, full-writer quota participation or crash recovery. Those remain required before integration/activation. No acceptance criterion above is marked satisfied by component tests alone.
