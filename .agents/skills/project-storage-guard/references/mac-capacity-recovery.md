# Mac capacity recovery in the user's chosen order

Apply this route when a Mac lacks space for the current project's next operation or when the user explicitly requests this project's cleanup. This is an operating policy, not evidence that any disk was cleaned, mounted, purchased, formatted, uploaded or backed up. Keep actual account addresses, folder IDs, mount bindings and quota receipts in the authorized private registry/configuration; public/project-portable text uses logical bindings only.

## Set the operation and finite target

- **Policy update:** edit instructions only. Do not touch product files or storage.
- **Inventory only:** read bounded metadata and propose specific candidates; do not clean or migrate.
- **Cleanup only:** carry out authorized routine project cleanup and suitable storage relief; report the verified result and stop without starting a build or product Goal.
- **Recovery and continue:** preserve the existing task, ownership, cumulative attempts and deadline; apply the route below and resume that task only after all affected volumes pass their original budget. Do useful independent light work if heavy work remains blocked.

Identify the actual writer, project and next operation before any write. Require measured `free >= additional peak + untouched reserve` on every affected volume, with simultaneous job peaks included. Use stricter project thresholds. Include archive creation, copy staging, upload cache, expanded assets and verification readback in peak estimates; measure physical free bytes, not just advertised cloud capacity or purgeable estimates. Missing peak/reserve or inaccessible state stays UNKNOWN.

Work in this exact evaluation order: **本案清理 → iCloud → 外接硬碟 → 指定 Google Drive**. A stage can be unavailable, unsuitable, insufficient, verified-success or verification-pending. Record its short reason and proceed to the next option when appropriate; do not reattempt the same failed transfer without a new correction or try every option after sufficient capacity has been recovered. Preserve the existing finite retry/deadline limits.

## 1. Clean only this project's safely reconstructible output

Start with known local output/log/temp/cache paths and bounded metadata; do not scan the whole home directory, all projects or cloud-placeholder trees. Map a cache outside the repo to this project using its actual producer/configuration, and check shared users before treating it as owned. A project-like folder name alone is insufficient proof.

Consider stopped superseded build output, abandoned owned temp output, bounded redundant debug bundles and rebuildable project-specific caches. Keep the current/rollback candidate, required symbols, distinct unresolved-failure evidence, source/WIP, tracker/memory, real databases, original assets, model revisions not recoverable from a verified source, signing material and unique saves. Do not erase a shared global cache, SDK, simulator, `.git`, environment, dependency tree or all `.run` contents merely because the path is large.

Choose small high-confidence candidates first. Confirm exact resolved paths, stopped writers, reproducibility with available inputs, retained evidence and scope authorization; prefer the tool's supported scoped cleanup when available. A request to clean this project's capacity authorizes routine proven rebuildable output cleanup, but not unrelated projects, unique-file destruction, cloud deletion, whole-Trash emptying or disk formatting. Avoid deleting caches needed immediately if the rebuild/download would cost more space than it frees.

Record the scoped action and measure actual resulting free bytes. Moving files into Trash on the same volume normally does not reclaim capacity; do not count it as recovered. Do not empty unrelated Trash to manufacture a result. If the next operation now passes, stop the fallback chain.

## 2. Assess iCloud for cold archives and local offload

Check the actual Apple Account/storage access, selected project archive location, cloud headroom, network, item eligibility and resident source bytes. Existing iCloud storage or a cloud icon alone does not prove upload completion. Never enable whole-Desktop/Documents synchronization, sign out, change global optimization settings or hydrate a whole project just to complete this route.

Choose immutable, no-longer-needed-local media, old verified candidates or closed snapshots that are within the current storage scope. Keep active Git worktrees, `.git`, agent configuration, live databases, current build inputs and concurrently written output resident on a suitable execution disk. If the current repo already sits in iCloud, do not offload its active tree or change sync settings during a writer's run; handle a deliberate relocation through its real handoff.

Use a versioned **copy** with a compact recovery manifest. Bound any archive and upload staging so it cannot fill the disk first. Verify completion, expected byte size and content identity through a supported cloud checksum or a bounded independent readback on a volume with room; a filename or sync animation is insufficient. Apple's status labels distinguish waiting uploads, ineligible items and cloud exhaustion. If reliable content/readback verification is unavailable, keep the source and mark verification pending rather than claiming it is safe to remove.

After verification, use the supported **Remove Download** operation for that exact eligible iCloud item to release its local downloaded copy when authorized. Do not delete the synced file or folder: deletion propagates to other devices. If the original remains outside iCloud, separately classify its local duplicate before any permitted removal. Re-measure disk free bytes; copying into iCloud on the same Mac may initially consume space, and offload may not immediately satisfy the target. Skip to the next stage if iCloud is full, unavailable, unsuitable, too slow within the budget, or cannot safely release enough space. Retain unique originals and pending transfers.

## 3. Assess a real external disk

A future purchase or a directory under `/Volumes` is not a mounted disk. Verify the actual volume UUID, mount/device identity, writable status, filesystem, resolved destination, free bytes and suitable reliability/performance. Preserve the disk's contents and format; never format, repartition, create a guessed mount directory or silently write to an internal fallback when the disk is absent.

Use the delivery skill's read-only external-disk preflight when available. For Mac-only development, APFS is a suitable format to evaluate; existing formats still need workload compatibility checks. Shared free capacity within one APFS container must not be counted independently for each volume. Internal temp, tools, simulator, swap and caches may remain internal even when output goes external; verify redirects and budget both volumes.

Copy only selected owned assets, archived candidates or supported project output/cache paths to a versioned project destination. Verify byte/hash identity, ability to reopen/read, producer configuration and an explicit recovery path before a permitted local-duplicate cleanup. No blind copy of a 70 GB tree merely to move a few GB of rebuildable output. Moving an active worktree requires its owner to stop writers, save unique WIP, preserve Git common-directory/worktree relationships, update the real workspace registration and verify the new path; the storage prompt alone must not bypass that handoff.

If disconnected, read-only, insufficient, incompatible or not yet available, record the condition and evaluate the final stage. Do not ask the user to buy, erase or reformat hardware as an automatic action.

## 4. Assess the designated Google Drive account

Resolve the requested account from the authorized private binding and verify the **actual authenticated account** before any upload; never silently use another Google account. Treat the user's reported 5 TB plan as a plan claim, then measure real remaining quota and the selected project's asset root. Google One storage is shared across Drive, Gmail and Photos; family usage, Trash, existing files and pending uploads can reduce headroom. Do not list unrelated folders just to find one project.

Use the existing authorized connector/transfer route with bounded resumable batches when supported. Store cold assets, weights, durable candidates and recovery checkpoints with a small manifest; follow `cloud-assets.md`. Do not turn on whole-Drive mirroring or use a streamed folder as an active repo, database or build cache to appear to gain 5 TB of local disk.

Streaming still consumes local cache; mirroring keeps local copies. On macOS using File Provider, the streaming cache is controlled by macOS and cannot be redirected to an external disk through Drive's cache-location setting. Inspect the actual client rather than assuming a cache redirect will work. Prefer an already available direct/resumable upload path when it avoids a duplicate staging copy; do not install a new sync daemon as an incidental fix.

Require the completed upload plus expected size/content verification and a recorded restore path before any allowed local cleanup. Retain the unique source if verification fails. Never delete a synced Drive file to free only local space, clear shared cache wholesale, empty cloud Trash or alter sharing under this policy. Re-measure real local free bytes after any supported local offload/removal; upload success alone does not recover local space.

## Close the route or resume

Leave a compact record in the original tracker/memory: current task, writer, volume/free-before/free-after, peak/reserve, selected exact paths, bytes actually copied/removed, each stage's result or skip reason, destination identity kept private as needed, hashes/readback, protected data, unresolved gap and next action. Distinguish logical file bytes from physical bytes reclaimed; compression, clones, hard links, snapshots and other live processes may make them differ.

If no stage meets the target, stop the unsafe heavy operation and state the exact missing capacity/access/verification. Preserve pending uploads and WIP, with no unbounded transfer retries. A cleanup-only task finishes here. An originally authorized development task may continue its independent light frontier, or resume the intended command after fresh ownership and capacity checks; do not create new product work or reset attempts/deadlines.
