# Route by the user's current situation

Select exactly one situation before generic setup or any write. Reuse explicit choices in this session; ask only when two materially different scopes remain. The current user request and selected scenario constrain the general delivery workflow. Installing this Skill does not itself start any scenario.

## Compose only the relevant contract

For portable v6.6 distributions, select the project/client/scenario prompt under docs/delivery-v6/scenarios/. Private Hub and Sites generate their copies from the same scenario templates. The four older top-level client files remain resume-compatible entry points; they no longer pretend to cover every lifecycle at once. Do not append the old all-lifecycle bootstrap after a new scenario.

Read the shared workspace/identity/material rules plus only the chosen scenario and relevant project profile. Planning/storage/rules must not inherit a blanket instruction to run every card. A reviewer stays read-only even for installer, tracker and generated output in the product tree. A worker without dispatch waits read-only; do not expand that into taking the entire product.

An explicit resume request or existing approval for the same concrete scope is sufficient to do already authorized work. Share a short continuation point, then act; ask a question only for a genuinely missing consequential choice. Do not introduce another approval just because the client, model or version changed.

## Interrupted work and Site counts

Use the selected project's complete available source-card projection and original task authority to identify the remaining scope. Record unknown/stale coverage. Separate accepted work with stale projection, ready work, dependencies, external waits and actual user decisions. Only matching acceptance evidence closes a card; a running/stopped agent event or declining backlog count is not acceptance.

A partial child, a tool completion or a finished analysis is a checkpoint. The coordinator must collect it and continue the next approved executable frontier while budget and authority remain. A valid blocker for one item does not block unrelated ready cards. Preserve task IDs/revisions, cumulative attempts, original deadline and scope across re-entry. Do not create new work, weaken AC or reset budgets to eliminate all visible cards.

## Capacity as a selected task or a dependency

The ordered Mac route is own-project cleanup → iCloud → verified external disk → designated Google Drive. Read the companion storage reference for its verification, local-free-space and protection rules. Store the user's actual account/mount/folder bindings in private configuration, not public kits. The advertised 5 TB plan is not verified available space.

If storage is the selected task, finish after the measured report. If capacity blocks an already authorized resume/recover/change task, preserve that task, resolve the resource issue, then recheck ownership and peak + reserve before returning to its next command. A request to update policies performs no cleanup or migration.

## Finite goals

Inspect existing goals and actual client capability before using a native Goal. Scope its condition to the selected scenario: resume/recover to the original approved frontier, change to that delta only, collaborate to the coordinator's authorized dispatch scope. Never give a joining worker/reviewer an entire-project goal.

Do not start product Goals for plan, storage, rules or a read-only review. Do not replace an existing goal, stack a continuation hook or reset its persisted deadline/attempt ledger. A text prompt or Site selection is not evidence that a Goal was created.
