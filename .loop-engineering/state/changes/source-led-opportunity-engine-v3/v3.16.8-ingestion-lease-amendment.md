# V3.16.8 official-ingestion lease amendment

Status: implementation subject pending fresh gates

## Production RED baseline

The reviewed V3.16.7 runtime run `54aa220b-e057-f8a8-092e-e455ba523bbf`
proved that the final facts claim can now cross the database role's former
two-minute statement timeout. It then exposed a separate failure while applying
official ingestion:

- 3,426 of 3,427 durable jobs succeeded and the final `facts_refresh` barrier
  was claimed by reviewed producer `b185896bb460f820e46e74092c2afcd202cbdfec`.
- Official acquisition completed and 11 immutable chunks / 1,260 items reached
  the staging plane.
- A 50-row financial-fact application occupied the managed transaction pooler
  longer than the closed 120-second lease. The last successful heartbeat was
  `2026-08-15T18:40:03Z`; the lease expired at `18:42:03Z` and the worker
  returned `lease_lost` without completing or publishing a projection.
- The installer safely restored the prior runtime and Web was not deployed.
  No password reset, destructive migration, LINE, dispatch or promotion ran.

This is an infrastructure failure, not evidence that the market has no research
candidates. The production site must not be updated until one reviewed producer
finishes the resumed immutable occurrence and publishes a compatible projection.

## Requirements

1. Every non-terminal official-ingestion application chunk is at most 20 rows,
   including trading sessions, financial facts, prices, corporate actions and
   reported valuations. Ordering, item conservation, chunk identities and the
   terminal root remain unchanged apart from the deterministic new chunk graph.
2. PostgreSQL heartbeat transport errors are retryable within the current
   120-second lease. Exhausting one reconnect window is not lease loss; a
   database `false` is immediate authoritative loss, while sustained inability
   to renew until five seconds before expiry fails closed.
3. After every successful bounded chunk apply, the main reviewed adapter must
   synchronously renew the exact run/job/token lease before starting the next
   chunk. This complements, and does not replace, the independent worker-thread
   heartbeat.
4. Replay of the interrupted run remains idempotent. A function-only additive
   claim upgrade exposes the exact partial staged prefix and chunk graph. The
   runtime must byte-verify that prefix, preserve its existing ordinals and
   append only a ≤20-row continuation; immutable official fact authorities
   cannot be overwritten and completion still requires the terminal root.
5. The change must not weaken the 60→30→20 candidate bounds, recommendation
   gates, point-in-time rules, credential isolation, exact reviewed runtime
   identity, V3 disabled route, or promotion/evaluation blockers.
6. Production activation must use a new exact reviewed commit and evidence
   commit, pass the protected Code Gate, resume to terminal success, prove a
   second same-occurrence no-change invocation, and only then deploy the same
   reviewed source to the existing Vercel project.

## Architecture

The durable execution boundary remains unchanged:

```text
reviewed handler
  -> <=20-row immutable chunk
  -> append/apply RPC (idempotent ledger)
  -> synchronous lease renewal
  -> next chunk

independent worker thread
  -> fresh bounded PostgreSQL client per attempt
  -> retry reconnect windows until near actual lease expiry
  -> false = immediate loss; deadline = fail closed
```

One additive, apply-twice-safe function upgrade is required; it adds no table,
column, destructive DDL or public mutation authority. The already-applied
V3.14/V3.15 tables and application ledger remain the recovery authority. The
resume path must consume the same source cutoff, byte-verify every immutable
staged prefix and retain the existing mixed legacy/new chunk graph.
