# V3.16.11 deterministic calendar-dependency recovery amendment

## RED production evidence

- Reviewed V3.16.10 producer `eaa4a33b-69f1-b9b0-1fd2-92e4ebf3a5ab`
  reached `facts_refresh` after 3,424 extraction jobs and persisted 960 trading
  sessions, 1,315 financial facts and 360 price observations.
- Price chunk ordinal 18 failed with typed SQLSTATE `PT409`, constraint
  `calendar_dependency_unavailable`; the reviewed installer automatically
  restored runtime `184390953048209730c22828548858c28fa3b6b7`.
- The failed occurrence cutoff was `2026-08-15T02:41:24Z`. The official
  authority for the last historical session was first recorded during the
  attempt, after that cutoff but before its database-owned terminal time.

## Contract

The normal scheduled/material occurrence remains byte-identical. A recovery
occurrence exists only when an immutable failed run has the exact persistence
diagnostic `calendar_dependency_unavailable` and official calendar authority
was recorded strictly after its cutoff and no later than its terminal time.
Its cutoff is exactly `date_trunc('second', failed.terminal_at)` and its ID is a
hash of the base occurrence, fixed cutoff, owner and scheduler configuration.
It never uses retry wall clock. All attempts and a retained success therefore
resolve the same logical occurrence.

Public point-in-time readers, the private price/calendar dependency resolver,
source/collection-time checks, the five-attempt bound, V3 disabled state and
all LINE/promotion prohibitions remain unchanged.

## Verification owners

- Fresh database applies the complete migration chain twice and verifies the
  resolver is `SECURITY DEFINER` and `VOLATILE`.
- Static regression proves the typed diagnostic, bounded authority window,
  database-owned terminal cutoff and stable recovery preimage.
- Production activation must resolve a cutoff later than the failed base
  cutoff, complete two exact producer invocations and retain the same success
  on the second invocation before Web deployment.
