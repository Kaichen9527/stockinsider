# Entity Link and Deduplication Contract: source-led-opportunity-engine-v3

Version: `entity-link-v3.1`

## Authoritative Identity

`instrument-roster-contract.md` supplies cutoff-valid active TWSE/TPEx common-stock symbols; existing `stocks` is only the bound internal ID/display projection. Additive `stock_aliases_v3` supplies aliases with `(alias_authority_id, stock_id, normalized_alias, source, source_timestamp, approved_by_principal_id, approved_at, valid_from, valid_to, status, normalization_version, recorded_at)`. At cutoff, first apply the alias stream `[stockId,normalizedAlias,source]` algorithm in `authority-supersession-contract.md`, including inactive/expired terminal events; only `effective_active` aliases may link. Exactly two write paths may create them.

1. `POST /api/internal/instrument-roster-v3` authenticates the fixed bearer `opportunity_runner`. In the same transaction as one official roster event, it appends exact `active|inactive` alias events required by `instrument-roster-contract.md`, only for that row's old/new official legal and short name streams, with `source=official_roster_seed`, the roster `stock_id/source_timestamp/validity`, `approved_by_principal_id` equal to the fixed official-roster ingestion principal, `approved_at=transaction_timestamp()` and independently database-generated `recorded_at`. Request-supplied alias text, status, principal or approval time is forbidden.
2. `POST /api/internal/stock-alias-v3` uses the exact dual-controlled `identity_reviewer` route catalog in `auth-principal-contract.md`, accepts one manually proposed alias bound to an existing roster stock, stores `source=manual_review`, `approved_at=transaction_timestamp()`, independently database-generated `recorded_at`, and only the verified principal ID; the fixed runner cannot call it.

The roster route rejects manual alias fields and an identity reviewer cannot invoke roster seeding. Both paths normalize before insert and store the same immutable algorithm version. Official seeds inherit business timestamps but neither `approved_at` nor `recorded_at` is backdated. Hand-coded `COMPANY_ALIAS_MAP` may be migration input only by submitting a new manual-review row through the second path; it is never runtime authority by itself. Duplicate normalized aliases across active stocks are ambiguous.

Each post-supersession alias row is `[aliasAuthorityId,normalizedAlias,stockId,source,sourceTimestamp,approvedByPrincipalId,approvedAt,validFrom,validToOrNull,status,normalizationVersion,recordedAt]` with manifest terminal code `effective_active|revoked_or_expired`; rows sort stock ID, normalized alias, source, valid-from, source timestamp, approved-at, recorded-at, approving principal and authority UUID. A latest differing tie is `authority_revision_conflict`. Under `manifest-storage-contract.md`, `algorithmVersion,sourceCutoff,rowCount` are the `alias_authority` header fields and row count includes every selected terminal stream. `aliasManifestHash` is the universal root hash; only `effective_active` rows populate the link trie, and active duplicate normalized aliases across stocks remain ambiguous. The 100,001st selected stream fails `identity_manifest_overflow`; the manifest is frozen before `seal_inputs` and no monolithic alias array is hashed in memory.

Normalize aliases with Unicode NFKC, trim, collapse whitespace, lowercase ASCII and remove the corporate suffixes `股份有限公司`, `有限公司`, `公司` only at the end. The stored normalized value and algorithm version are immutable evidence.

## Documents and Claims

- `canonicalDocumentId = SHA256(UTF8(RFC8785([sourceKey,approvedSourceIdentityId,normalizedCanonicalUrl || stableConnectorDocumentId])))` in lowercase hexadecimal; array tagging prevents delimiter collisions.
- Canonical URLs must be absolute `http` or `https`. Before parsing, any `%` not followed by exactly two ASCII hex digits makes the document `parse_failure`. Parse with the WHATWG URL algorithm; any parse failure does likewise. Lowercase scheme and ASCII/IDNA host, remove user-info and fragment, remove port 80 for HTTP or 443 for HTTPS, resolve dot segments, and use `/` for an empty path. In path/query components, percent-decode only RFC 3986 unreserved bytes, encode all other non-ASCII/unsafe bytes as UTF-8 percent triplets with uppercase hex, retain literal `+` as `+`, and never translate it to space. For a non-empty raw query, split on every `&` while retaining empty elements; split each element on its first `=` (missing `=` means empty value), normalize key/value, and canonicalize every retained pair as `key=value`, so an empty element is `=`. An empty raw query has zero pairs and no trailing `?`. Remove a pair when its normalized ASCII-lowercase key is `fbclid`, `gclid` or begins `utm_`. Retain repeated remaining pairs; stable-sort by normalized key, normalized value, then original zero-based pair ordinal and join with `&`. Remove a trailing path slash only when the path is not `/`. Connector URLs that differ only by these rules have one normalized URL.
- Acquire only the immutable complete revision and versioned per-connector allowlisted fields from `source-adapter-contract.md`. Strictly decode UTF-8, remove one leading U+FEFF per field, normalize CRLF/CR to LF, then Unicode NFKC; required-field absence or invalid encoding produces `parse_failure`. The canonical content preimage is RFC 8785 canonical JSON of `[[fieldKey,normalizedFieldValue],...]`, including supported empty optional fields and transcript segments as `[timestamp,text]` pairs sorted timestamp then connector segment ID. `contentHash = SHA256(UTF8(canonicalContentPreimage))` in lowercase hex.
- No text is truncated for hashing. Acquisition streams at most 100,001 Unicode code points across the normalized field values; observing code point 100,001 terminates `parse_failure` with zero claims/mentions and no content hash. Order is: canonical-document-ID duplicate check; encoding/required-field/size validation; content-hash computation and distribution-scoped duplicate check; claim splitting/parsing. Within one source-scan run and one `(sourceKey, approvedSourceIdentityId)` distribution, a later selected row with an already seen canonical document ID or computed content hash terminates `duplicate_document`. Content hashes are never deduplicated across distribution identities; cross-platform copies parse, then identical claim IDs dedupe and distinct distributions contribute reach.
- Build `claimSourceText` by taking normalized field values in the same allowlisted field order, using transcript segment text in its canonical timestamp/segment-ID order, and joining adjacent values with exactly one U+000A boundary; field keys/timestamps are not claim text. Before delimiter scanning, form `claimSplitText` by replacing every maximal substring that begins with case-insensitive ASCII `http://` or `https://` and continues through the code point immediately before the next Unicode whitespace or end-of-text with one U+0020. URL punctuation therefore cannot create a claim boundary or a ticker/alias occurrence. Split `claimSplitText` left-to-right on each single delimiter code point U+000A, `。`, `！`, `？`, `.`, `!`, or `?`, except that the ASCII period inside a retained `.TW`/`.TWO` lexeme or recognized non-TW suffix lexeme from the next bullet is not a delimiter. Consecutive delimiters may create empty segments, which are discarded. Segments above 500 Unicode code points split into consecutive 500-point chunks. For each segment, form `claimScanText` by NFKC and mapping ASCII A-Z to a-z; ticker/alias spans and offsets are computed on this text. Derive `normalizedClaimText` from `claimScanText` by replacing each maximal run of Unicode General Category `P*` or `Z*` characters or ASCII whitespace U+0009..U+000D with one U+0020, trim U+0020 at both ends, and retain all other code points including numbers and currency/math symbols. A segment with empty normalized claim text and no retained occurrence is discarded.

The validated concatenated text is capped at 100,000 Unicode code points and 1,000 potential-stock occurrences before any claim is emitted. Exceeding the occurrence cap produces `parse_failure` with zero extracted claims/mentions. The 500-point chunk rule bounds a processed document to 200 claims.
- Build mention spans over `claimScanText` Unicode code points using ASCII digits/letters. Explicit lexemes are exactly: TW-suffixed `(?<![0-9A-Za-z])([0-9]{4})\.(tw|two)(?![0-9A-Za-z])`; recognized non-TW-suffixed `(?<![0-9A-Za-z])([0-9A-Za-z]{1,6})\.(us|nyse|nasdaq|hk|hkg|jp|t|ks|kq|ss|sz)(?![0-9A-Za-z])`; prefixed `(?<![0-9A-Za-z$#])([$#])([0-9]{4})(?![0-9A-Za-z])`; and bare `(?<![0-9A-Za-z$#])([0-9]{4})(?![0-9A-Za-z.])`. These suffix alternatives are the entire recognized non-TW set for V3 and matching is ASCII-case-insensitive after scan-text lowercasing. Scan left-to-right; for overlapping lexemes containing the same base span keep recognized non-TW suffix before TW suffix before prefix before bare, then the longest full lexeme. `startOffset/endOffset` cover the full retained lexeme with end exclusive and mode is `ticker`. A TW/prefix/bare `normalizedToken` is the four digits; a recognized non-TW token is the complete lowercase `base.suffix`, which can never resolve against the Taiwan roster and terminates by the first reason rule. For exact aliases, scan the cutoff-valid alias trie from every code-point offset, keep the longest matching normalized alias at that start, retain all stock mappings for the same retained alias/span to permit ambiguity, and resolve equal-length alias text lexicographically. Exact-alias scanning therefore works inside unsegmented Chinese text. A span overlapping an explicit ticker lexeme is not emitted as an alias.
- Fuzzy matching applies only to maximal non-whitespace/non-punctuation lexical runs of 2..40 code points that produced neither an explicit ticker nor exact-alias span; it never enumerates arbitrary substrings of an unsegmented run. Compare the entire run with cutoff-valid aliases under the stated Levenshtein rule. Alias manifests contain at most 100,000 active aliases of 2..40 code points; overflow fails identity-manifest creation rather than truncating. After the document-level 1,000-occurrence cap, spans sort by start offset, end offset, then mode order `ticker,exact_alias,fuzzy`, then normalized token.
- `canonicalPotentialSymbolTokens` is RFC-8785 canonical JSON of every retained occurrence as `[normalizedToken,startOffset,endOffset,mode]`, sorted by normalized token, start, end and mode while retaining repeated occurrences. `canonicalClaimId = SHA256(UTF8(RFC8785([normalizedClaimText,occurrenceArray])))` in lowercase hex. Only identical claim IDs inside the run are duplicate claims. V3 does not guess semantic/paraphrase equivalence. `evidenceRootId` is `SHA256(UTF8(normalizedUnderlyingUrl))` for an explicitly cited normalized official/research URL, otherwise the canonical claim ID; it affects evidence independence only, not claim outcome.
- `claimEvidenceStance` is a parser-owned persisted enum under literal version `claim-evidence-stance-v3.0`. Starting from the already derived `normalizedClaimText`, test the following ordered literal prefix set longest-prefix first, then UTF-8 byte order for equal lengths: `["不會","並未","否認","尚未","未","沒有","無","取消","停止","終止","撤回","駁斥","not","no","never","denies","denied","deny","cancelled","canceled","withdrawn","false"]`. A Chinese prefix matches at byte zero without a following-boundary requirement. An ASCII prefix matches at byte zero only when the next code point is absent or U+0020. The stance is `contradicts` exactly on a match and `supports` otherwise. No interior substring, morphology, model output, later projection, or live text can change this value. The source parse result stores it with the claim occurrence, and every later evidence/detail row copies it byte-for-byte. This conservative grammar deliberately leaves an unrecognized contradiction as `supports`; changing the prefix set or matching rule requires a new stance version and therefore a new `sourceFunnelPolicyHash`.

Every emitted claim has a zero-based `claimOrdinal` in document split order, even when its hash repeats in the same document. For a duplicate claim, the first prior occurrence in effective timestamp, document ID, then claim ordinal order is canonical. Paraphrases have distinct claim IDs; if they explicitly cite the same upstream evidence root, they cannot add an independent verification class. `deduplicatedReach` is the number of distinct `(sourceKey, approvedSourceIdentityId, canonicalDocumentId)` tuples in its cluster; repeated rows of one tuple count once.

## Potential-stock Mentions and Reasons

A potential-stock mention is a retained span above: a four-digit token, `$`/`#` plus a four-digit token, a `.TW`/`.TWO` ticker, one exact recognized non-TW suffixed lexeme, an exact normalized authoritative alias, or a fuzzy lexical-run candidate produced at similarity >=0.50. Recognized non-TW lexemes bypass alias/fuzzy comparison and always terminate `unsupported_instrument/unsupported_market`. Fuzzy similarity is `1 - LevenshteinDistance(normalizedToken, normalizedAlias) / max(tokenLength, aliasLength)` over Unicode code points; aliases/tokens shorter than two code points are not fuzzy candidates. Compare against every cutoff-valid alias and retain all equal-best stocks for ambiguity evaluation. Each retained occurrence has a stable left-to-right ordinal and exactly one outcome/reason.

Reason enum:

- linked: `explicit_ticker_context`, `exact_unique_alias_context`;
- ambiguous: `ambiguous_number`, `ambiguous_alias`, `fuzzy_below_auto_threshold`;
- rejected: `below_min_confidence`, `inactive_or_unknown_symbol`, `missing_stock_context`;
- unsupported: `unsupported_market`, `non_common_stock`, `unsupported_instrument_type`;
- duplicate: `duplicate_claim_link`.

Reason selection is first-match and mode-specific, so one occurrence cannot satisfy two terminal reasons:

1. A recognized non-TW exchange suffix -> `unsupported_market`; a recognized TW roster row whose type is ETF/ETN/warrant/preferred/depositary receipt/bond -> `non_common_stock`; any other recognized ineligible type -> `unsupported_instrument_type`; an absent or inactive symbol -> `inactive_or_unknown_symbol`.
2. For an explicit four-digit ticker, a year/common-number token without the enhanced context below -> `ambiguous_number`; any other missing stock context -> `missing_stock_context`; otherwise -> `explicit_ticker_context`.
3. For an exact alias, more than one cutoff-valid active common stock -> `ambiguous_alias` before context evaluation; a unique alias without stock context -> `missing_stock_context`; otherwise -> `exact_unique_alias_context`.
4. For a fuzzy run, best similarity below 0.65 -> `below_min_confidence`; similarity 0.65 through 0.849, any equal-best multi-stock match, or any fuzzy run lacking auto-link authority -> `fuzzy_below_auto_threshold`. Fuzzy matching never produces an automatic linked reason in V3.

Outcome mapping is fixed: linked reasons produce `linked_new` or `linked_refresh`; a link in a duplicate claim produces `linked_duplicate_claim`; ambiguous reasons produce `ambiguous_symbol`; rejected reasons produce `rejected_low_confidence`; unsupported reasons produce `unsupported_instrument`. Duplicate-claim classification is applied after the underlying unique-claim link reason and changes only a linked outcome to `linked_duplicate_claim`/`duplicate_claim_link`; it cannot overwrite an ambiguous, rejected or unsupported outcome.

Confidence is 1.00 for valid explicit ticker plus context, 0.90 for exact unique active alias plus context, and similarity clamped to at most 0.84 for fuzzy/name-only candidates. Missing context caps confidence at 0.64. A linked symbol already present in the active candidate ledger is `linked_refresh`; otherwise it is `linked_new`.

Stock context is evaluated in the 28 Unicode code points before/after the token. It exists when the window contains the cutoff-valid official/alias name, a `$`/`#` ticker prefix, `.TW`/`.TWO` suffix, or one of this versioned case-insensitive vocabulary: `股`, `股票`, `代號`, `股號`, `標的`, `公司`, `台股`, `上市`, `上櫃`, `買`, `賣`, `法說`, `營收`, `EPS`, `PE`, `目標價`, `停損`, `外資`, `投信`, `自營`, `漲停`, `跌停`, `突破`, `回測`. A year-like `19xx`/`20xx` or one of the exact common price/quantity tokens `1000`, `1200`, `1500`, `1600`, `1700`, `1800`, `2000`, `3000`, `5000` still requires a cutoff-valid name, ticker marker/suffix, `代號` or `股號`; generic vocabulary alone cannot resolve it.

For every emitted mention, source parsing also freezes the one private human-review context slice from `claimScanText`: start at `max(0,startOffset-28)` and end at `min(claimScanTextCodePointLength,endOffset+28)`. Store that exact NFKC/ASCII-lowercased slice as `reviewContext`, with mention-local offsets `reviewMentionStartOffset=startOffset-sliceStart` and `reviewMentionEndOffset=endOffset-sliceStart`. The slice is 2..96 Unicode code points and at most 384 UTF-8 bytes; the local offsets satisfy `0 <= start < end <= reviewContextCodePointLength`. It is never reparsed to change the engine outcome and is not public source prose. It exists solely as immutable, hash-bound evidence for the dual-controlled link-audit assignment in `shadow-evaluation-contract.md`; public serializers, logs, generic RPC audits and error bodies must never emit it.
