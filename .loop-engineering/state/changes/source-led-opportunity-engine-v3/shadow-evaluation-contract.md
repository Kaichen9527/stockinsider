## Cohort

The canonical daily cutoff for a completed Taiwan trading date is exactly the `canonicalCutoff` returned by the composite authority in `trading-calendar-contract.md`; a weekday, price-presence or current-calendar inference is forbidden. `evaluationDatasetLockHash` is a static approval hash over evaluation code, calendar/provider extraction rules and the frozen legacy lock; it is not a daily row-data manifest and must be identical across every date compared in one evaluation. `runtime-transaction-contract.md` v3.17 derives and stores that exact non-null value for `production_shadow_daily|backtest_daily_primary|outcome_label_daily|shadow_evaluation_daily`, stores null only for `ad_hoc_shadow`, and includes the purpose-owned value in preparation and logical keys. `comparisonContractKey` is separately the exact static comparison-contract identity from `data-contract.md`. The completed `evaluation_input` header, every included run and any assistive-artifact registration claiming that evaluation must carry the same `comparisonContractKey`; artifact selection requires equality to the consuming `opportunity_runs.comparison_contract_key`. Neither `evaluationDatasetLockHash` nor the legacy baseline-lock hash can substitute. Evaluation consumes only server-owned run purposes `backtest_daily_primary` and `production_shadow_daily`; every other purpose is ineligible. For each `(runPurpose,tradingDate,tradingDateAuthorityHash,comparisonContractKey,evaluationDatasetLockHash)` the database permits one terminal successful `enrich_rank` lineage, with retries sharing its preparation/final logical idempotency keys. Zero successful lineages makes that date typed unavailable; more than one is evaluation-integrity failure for the whole manifest, never a choice among runs. The run must have the exact canonical cutoff and applicable trading-date authority hash. Every direct entry/outcome price ref additionally resolves under and binds the exact `priceProviderAllowlistHash` from `market-contract.md`; evaluation cannot choose a price provider or corporate-action algorithm.

For each completed Taiwan trading date, build the raw common cohort from that unique canonical V3 run's deep-research symbols and the frozen legacy visible union using only data whose source timestamp is at or before that cutoff. The legacy union at code ref is first occurrence while concatenating `opportunities`, `scenarioUpsideCandidates`, `hotTracking`, `earlyWatchlist`, then `earlySignals`, retaining the first 20 unique TW symbols. Before either engine ranks, remove a symbol unless the identical entry/outcome price facts and qualifying sector benchmark can label it for both engines; store every typed exclusion. This shared filtering prevents differential backfill. A run date is metric-qualifying only with at least ten remaining symbols.

V3 ranking key is the higher of momentum and swing score (tie chooses swing), then that horizon's confidence descending, then symbol ascending. Legacy preserves the concatenation order above. Over the filtered identical cohort, a symbol an engine cannot score/rank sorts below all its scored/ranked symbols, tied by ascending symbol; take each engine's first `min(20,filteredCohortSize)`. No post-ranking removal or backfill occurs.

Entry is the official close of the first completed Taiwan trading session strictly after `sourceCutoff`; same-session close is forbidden even when a run finishes before close. Sector entry and outcome alignment use the same session calendar and the immutable equal-weight construction in `sector-benchmark-contract.md`. If no official entry close or qualifying sector benchmark exists, the symbol/date is unevaluable and the run records the typed exclusion before metric denominators are formed.

At an evaluation cutoff, first materialize the ordered roster of all prior 252 completed Taiwan sessions and record for every date its unique canonical attempt/success or typed absence/failure; fewer than 252 calendar sessions is `provider_unavailable`, while omitting any member from an available 252-session window is integrity failure. From that fixed roster enumerate metric-qualifying successful `backtest_daily_primary` dates, sort trading date descending, retain the most recent `min(120,qualifyingDateCount)` distinct dates, then emit them in ascending date order. The manifest stores the evaluation cutoff, `evaluationDatasetLockHash`, exact 252-date attempt roster, actual `backtestCount=0..120` and that exact ordered set. A count below 120 is a complete, non-promoting partial manifest: backtest metrics are null and the exact gate fact is `insufficient_backtest_dates`; it is not a failed manifest and no older non-qualifying date fills a seat. Older qualifying dates beyond 120 remain in the roster but are excluded from metrics. Separately enumerate `production_shadow_daily` canonical runs whose 20-session horizon matured at/before the evaluation cutoff, enforce one unique run for each distinct trading date under the same comparison/evaluation lock, sort maturity session descending then trading date descending, and retain the most recent 20 distinct dates. `liveCount=0..20` is always stored; fewer than 20 is the exact non-promoting gate fact `insufficient_live_dates`. Duplicate-date or duplicate-success lineage still fails integrity rather than producing partial evidence or filling a seat. Therefore an empty/immature daily evaluation is observable and reproducible but can never promote.

## Labels

From entry close to the next 20 completed Taiwan sessions:

- `return20Pct`: close-to-close return.
- `sectorRelativeReturn20Pct`: return minus sector-index return.
- `mfe20Pct`: maximum high-to-entry return.
- `mae20Pct`: minimum low-to-entry return (zero or negative).
- `sectorRelativeMfe20Pct`: maximum, over the same 20 sessions, of candidate high-to-entry return minus the sector index's close-to-entry return for that session.
- binary relevance: `mfe20Pct >= 10` AND `sectorRelativeReturn20Pct >= 5` AND `mae20Pct >= -8`.
- graded relevance for NDCG: 3 when `sectorRelativeMfe20Pct >=15`; 2 when >=10; 1 when >=5; otherwise 0. If `mae20Pct < -12`, cap grade at 1.

At `session_60|session_120|session_250` store the same return, sector-relative return, MFE and MAE fields when mature; these do not gate the first homepage-order promotion. `session_20` owns the promotion cohort values.

## Metrics

### Non-authoritative strategy bake-off

The `evaluation_bundle` filters the same frozen direct-candidate deep-success snapshot set into exact strategy order `official_only,source_led,hybrid`. Its supplying run IDs are exactly the first-seen union of the bound complete `evaluation_input.backtest_rows[*].enrichRunId` followed by `live_rows[*].enrichRunId`, with byte-equal overlap retained once; attempt-roster-only, excluded-date, foreign-manifest, wrong-lock/key and after-cutoff runs fail the bounded evaluation read. A row enters that common population only when its stored origin fields are exactly `directSource=true,candidateOrigin=direct_candidate,anchorClaimId!=null` and `deepStatus=succeeded`; comparison-only shallow observations are excluded before `preCapIdentities` and never appear as a selected or excluded strategy identity. Definitions, candidate eligibility, the common at-most-400 population and product-value formulas are owned by `hybrid-product-amendment.md`. Before the three rows, the result stores `[preCapCandidateCount,preCapOrderedIdentityHash,deferredDueStrategyEvidenceCap,retainedCandidateCount]`, where the hash is exactly `SHA256(UTF8(RFC8785(["strategy-population-v3.0",preCapIdentities])))`, `retainedCandidateCount=min(preCapCandidateCount,400)` and `deferredDueStrategyEvidenceCap=preCapCandidateCount-retainedCandidateCount`. The last value is at most 400 and all three strategies partition that exact retained identity set. The result contains one row per strategy:

`[strategy,selectedCandidateIds,excludedCandidateIdsAndReasons,selectedCount,verifiedChangePrecisionNumerator,verifiedChangePrecisionDenominator,verifiedChangePrecisionOrNull,contradictionCaptureNumerator,contradictionCaptureDenominator,contradictionCaptureRateOrNull,timeToFirstVerifiedChangeMinutesOrNull,reviewerResolutionNumerator,reviewerResolutionDenominator,reviewerResolutionRateOrNull,facts]`.

Candidate IDs are the ordered unique `[runId,symbol]` identities from the common retained set; exclusions use only the four closed reasons and strategy-specific precedence from `hybrid-product-amendment.md`. Counts are nonnegative safe integers; finite rates are 0..1; time is a nonnegative finite number rounded half away from zero to two decimals. A zero denominator produces null and the unique fact `insufficient_product_value_evidence`. These rows are database-computed inside the bounded evaluation read, then stored inside the immutable evaluation job result and evaluation evidence bundle; they add no normalized strategy table, RPC, promotion conjunct or domain influence. The complete computation summary canonical bytes must be <=262,144 at the maximum valid 400-candidate fixture.

- `Precision@20 = relevant symbols in top 20 / min(20, cohort size)`.
- `NDCG@20` uses the graded relevance above and standard `2^rel - 1` discounted by `log2(rank+1)`.
- Per run, `worstDecileMae20Pct` is the Hyndman-Fan Type-7 p10 of that engine's selected per-symbol `mae20Pct` values (more negative is worse); promotion uses the macro-average of those per-run p10 values.

Compute Precision/NDCG and the stated Type-7 adverse-excursion quantile per qualifying run, then arithmetic macro-average across run dates so repeated symbols do not dominate. Precision's denominator is `min(20,filteredCohortSize)`; NDCG's ideal ordering uses the same filtered cohort and cutoff. Excluded/non-qualifying dates do not enter any engine denominator and their counts/reasons remain evaluation evidence.

## Promotion Rule

Let relative improvement be `(v3 - legacy) / max(abs(legacy), 0.01)`.

- V3 Precision@20 relative improvement >=10%.
- V3 NDCG@20 relative improvement >=10%.
- V3 `worstDecileMae20Pct >= legacy worstDecileMae20Pct - 2.0` percentage points.
- Source-link accounting, acceptance, security and operational gates pass.

The Precision/NDCG/MAE improvement conditions are computed only when `backtestCount=120` and compared with the frozen legacy metrics for that same manifest. With a smaller count, both engines' metric objects are literal JSON null and every metric-improvement boolean is false. The 20 live cohorts are a separate conjunctive runtime-maturity/operational-evidence gate and are not mixed into, or substituted for, backtest macro-averages. With `liveCount<20`, the live-maturity boolean is false. All conditions are conjunctive. Failure or missing evidence keeps `mode=shadow`.

## Source-link Review Protocol

Promotion also requires reviewed link precision >=95% and recall >=90%. The audit population is every potential-stock mention from the evaluation manifest's actual selected `0..120` backtest dates plus actual `0..20` matured live cohorts; identical `(runId,claimId,mentionOrdinal)` appears once. A partial evaluation therefore still creates reproducible audit evidence but cannot promote on counts. Every mention records exactly one link mode (`ticker`, `exact_alias`, `fuzzy`) from the token class that created it and exactly one outcome family: `linked` for the three linked outcomes, `ambiguous`, `rejected`, or `unsupported`. Strata are the non-empty `(connector,linkMode,outcomeFamily)` tuples sorted lexicographically.

Let `P = min(400,populationCount)` and `S = nonEmptyStratumCount`. If `P=0`, require `populationCount=S=0`, emit empty `strata` and `samples`, set precision/recall null and fail their promotion booleans; no division is performed. If `P=populationCount>0`, review all mentions. Otherwise `P>0` and `S>0`: assign each stratum `min(stratumSize,floor(P/S))`. Allocate remaining seats over residual counts with Hamilton largest remainder: compute each uncapped stratum's ideal share `remainingSeats * residualCount / totalResidual`, assign floors capped by residual count, then assign leftover seats by fractional remainder descending and stratum key ascending. Recompute on remaining residual capacity until exactly P seats are assigned. The closed `allocationVersion` is `link-audit-hamilton-v3.0`.

For each unique population identity define `selectionHash = SHA256(UTF8(RFC8785(["link-audit-selection-v3.0",runId,claimId,mentionOrdinal])))`. Within each stratum choose ascending selection hash, then run UUID, claim UUID and mention ordinal until its exact allocation is filled. A `strata` row is `[connector,linkMode,outcomeFamily,populationCount,allocatedCount]`, lexicographically ordered by the first three fields. A `sampleId` is `SHA256(UTF8(RFC8785(["link-audit-sample-v3.0",evaluationManifestHash,runId,claimId,mentionOrdinal])))`.

For that exact mention, form `reviewEvidence=[sourceKey,evidenceRef,reviewContext,reviewMentionStartOffset,reviewMentionEndOffset,normalizedToken,linkMode,engineOutcome,engineReason,engineCanonicalSymbolOrNull]` from its stored mention plus owning claim; it is not reconstructed from current raw payload or authority. `reviewEvidenceHash = SHA256(UTF8(RFC8785(["link-audit-review-evidence-v3.0",runId,claimId,mentionOrdinal,reviewEvidence])))`. A `samples` row is `[sampleId,connector,linkMode,outcomeFamily,runId,claimId,mentionOrdinal,selectionHash,reviewEvidence,reviewEvidenceHash]`, sorted stratum order then selection hash, run UUID, claim UUID, mention ordinal. Header counts must equal these rows, every evidence hash must recompute, each allocation must equal its sampled row count, allocations sum to `P`, every sampled identity/evidence tuple must byte-match one exact evaluation-population mention and duplicate/conflicting identities fail integrity. The maximum 400 slices and their canonical overhead fit the generic 3 MiB bundle and 400-row section bound. These are the complete native sections of logical kind `link_audit_sample` under `manifest-storage-contract.md` v3.10; its universal root's opaque manifest ID is `sampleManifestId` and every durable sample/label key is `(sampleManifestId,sampleId)`. This remains valid when a stratum has fewer than ten rows or when the number of strata is large; no minimum-ten exception may overflow P.

After the sample root completes and before `evaluation_bundle`, `shadow_evaluate` builds exactly one cutoff-bound `link_audit_resolution` manifest. `evaluationCutoff` is database-derived and must byte-equal all three existing authoritative values: the `shadow_evaluate` run's normalized whole-second UTC `source_cutoff`, the bound `evaluation_input` header's `evaluationCutoff`, and the generic resolution manifest's `source_cutoff`; a null or mismatch is `data_integrity_failure` before any resolution page is created. Its header is `[evaluationCutoff,sampleManifestId,sampleManifestHash,resolvedCount,unresolvedCount]`. It selects only immutable labels with `recordedAt <= evaluationCutoff`; later labels cannot enter this run. In sample-manifest order, each sample appears in exactly one section:

- `resolved_rows`: `[sampleId,resolutionKind,canonicalSymbolOrNull,noLink,orderedLabelHashes,resolvedAt]`, where `resolutionKind` is `reviewer_agreement|terminal_adjudication`. Reviewer agreement requires the two distinct reviewer-role labels to have byte-equal `(canonicalSymbolOrNull,noLink)` and orders their hashes by reviewer role; terminal adjudication requires the two disagreeing reviewer labels plus the terminal adjudicator label and orders all three hashes `reviewer_1,reviewer_2,adjudicator`. `resolvedAt` is the greatest included label `recordedAt`.
- `unresolved_rows`: `[sampleId,resolutionState,orderedVisibleLabelHashes]`, where `resolutionState` is first match `missing_reviewer_1|missing_reviewer_2|reviewer_disagreement_pending_adjudication`; hashes are in reviewer-role order and include only cutoff-visible labels.

The combined rows equal the sample manifest's exact sample count, identities/order/hash refs byte-match it, header counts equal section counts and the manifest has at most 400 rows. Missing/extra/duplicate samples, labels recorded after the cutoff, illegal role combinations or a differing terminal resolution fail manifest completion. Its universal root is `linkAuditResolutionManifestHash`; retrying the same logical run reuses the same bound sample and resolution roots. Evaluation reviewer-resolution numerator is `resolvedCount`, denominator is `resolvedCount+unresolvedCount`, and no evaluation read may join `opportunity_link_audit_labels` directly.

Two independently authenticated `link_reviewer` principals label canonical symbol or `no_link` using the cutoff-valid alias/stock authority and the exact bounded `reviewEvidence` returned with their assignment. Disagreement requires a `link_adjudicator` principal distinct from both reviewers; verified principal IDs, database-generated `recordedAt` and blinded labels are immutable. Assignment/read and label writes use only `/api/internal/opportunity-link-audit-v3/reviewer-assignment`, `/api/internal/opportunity-link-audit-v3/reviewer-label`, `/api/internal/opportunity-link-audit-v3/adjudicator-assignment` and `/api/internal/opportunity-link-audit-v3/adjudication` under the dual bearer/signature, nonce, role and blind-read protocol in `auth-principal-contract.md` v3.8; the base path `/api/internal/opportunity-link-audit-v3` has no handler. The shared bearer is required as the coarse internal guard but cannot act alone or supply actor identity, request-body actor fields are rejected, and a reviewer cannot read the other label before submission. `precision = correct automatic links / reviewed automatic links`. `recall = correct automatic links / reviewed mentions adjudicated as linkable`. A zero denominator fails closed. The exact sample manifest/hash, counts by stratum and adjudication record are promotion evidence; model-generated labels are forbidden.
