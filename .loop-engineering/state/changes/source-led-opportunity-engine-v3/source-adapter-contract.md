# Source Adapter and Revision Contract: source-led-opportunity-engine-v3

Version: `source-adapter-v3.3`

## Immutable ingestion boundary

V3 never parses `source_raw_documents.content_text`, broker summaries, event summaries or legacy symbol arrays as authoritative source text. Each acquisition connector must append one `source_document_revisions_v3` row before its existing lossy/truncated legacy projection. The V3 append and legacy write are deliberately independent: a V3 append failure is recorded as connector degradation and makes that document unavailable to V3, while the legacy connector may continue unchanged. A legacy write failure never deletes or mutates an accepted V3 revision.

The route obtains the complete allowlisted fields directly from the connector result before any `SOURCE_RAW_CONTENT_MAX_CHARS` truncation. Existing rows may be backfilled only when every required raw field is still complete and its provenance is cutoff-auditable. Backfill uses the database transaction time as `recordedAt`; it never copies an old `created_at` into knowledge time. Truncated, summary-only or provenance-incomplete legacy rows are not reconstructed and produce no V3 revision. This prevents a backfill performed today from entering yesterday's manifest.

`source_document_revisions_v3` is append-only. Corrections append a new UUID revision for the same document family. Each revision binds both the stable source identity and the exact discovery-identity authority UUID accepted at acquisition. The caller supplies only `sourceIdentityAuthorityId`; `append_source_document_revision_v3` locks that authority stream, requires the referenced UUID to be its one current `effective_active` event at the function's captured database transaction timestamp, and copies `approvedSourceIdentityId=authority.sourceIdentityId` plus `sourceKey=authority.sourceKey` into the revision. Neither derived value exists in `source_document_revision_input_v3`, and the database composite FK independently enforces the copied triple. A null identity, stale/revoked authority, source-key mismatch or attempted independent identity/key is rejected before any revision/audit write. `recordedAt` is database-generated with `clock_timestamp()` and cannot be supplied or updated by a caller. After deriving `revisionFamilyKey`, the append RPC always takes the `sourceKey` registry lock and then the exact family lock. It atomically creates the immutable registry row for a first family only when the indexed ASCII-key probe with literal `LIMIT 1000001` proves fewer than 1,000,000 registered families for that source key; family 1,000,001 is `PT409/bound_violation`. It then reuses a byte-identical semantic duplicate and probes the stream-leading index with literal `LIMIT 65`; one family admits at most 64 retained immutable revisions across its lifetime, and a 65th distinct revision is `PT409/bound_violation`. Machine ingestion has no nonce; either bound failure writes no registry, revision or RPC-audit row under the exact runner route in `auth-principal-contract.md` v3.8.

`revisionFamilyKey = SHA256(UTF8(RFC8785(["source-revision-family-v3.3",sourceKey,approvedSourceIdentityId,stableConnectorDocumentId])))` as lowercase hex. `stableConnectorDocumentId` is nonempty and immutable; an adapter using `family_uuid` mints it once for the first acquisition and every correction reuses it. `adapterVersion` is literal `source-adapter-v3.3`; another value is rejected. `supersedesRevisionId`, when non-null, must reference an earlier revision with the same family key; cross-family, forward and cyclic edges fail at ingestion. The pointer is audit evidence and never overrides the deterministic selection rule.

Source-scan first enumerates every immutable `source_revision_family_registry_v3` key for the exact registry `sourceKey` in ASCII `revisionFamilyKey` order through the matching index with literal `LIMIT 1000001`, before reading or filtering any revision timestamp, source authority, published time, acquisition status or eligibility field. Row 1,000,001 is `bound_violation`; it is never discarded as future or ineligible. For each of the at most 1,000,000 registered keys, query that exact stream through its stream-leading index with literal `LIMIT 65`; row 65 is integrity failure. Only inside this already finite set does source-scan filter revisions to the exact `(sourceIdentityAuthorityId,approvedSourceIdentityId,sourceKey)` triple present as one `effective_active` terminal row in the frozen `sourceIdentityAllowlistManifestHash`, `recordedAt <= sourceCutoff`, `collectedAt <= sourceCutoff`, null `publishedAt` or `publishedAt <= sourceCutoff`, and the static lookback/eligibility rules in `source-matrix.md`. It never tests authority UUID membership without also testing both copied equality fields. A registered family with no cutoff-eligible revision contributes no selected document but was still bounded/enumerated. Within each family, the selected eligible revision has greatest `recordedAt`. If two rows share that greatest timestamp, every authoritative column other than `revisionId` must be byte-equivalent; otherwise the family fails `data_integrity_failure`; equivalent rows retain the lexicographically lowest lowercase revision UUID. Acquisition status participates in that equivalence. A later typed-failure correction therefore becomes the selected `parse_failure` rather than silently reviving an older complete payload.

Only the selected row per family enters eligible-document counting, ordering, scan-cap selection, eligible pages and the dataset-manifest tuple. Older/superseded rows remain immutable audit history but contribute neither a second eligible document nor a hidden hash input. A newly selected correction changes the tuple through its recorded time, payload/status, supersedes ref and revision ID. The registry-first `LIMIT 1000001` and database-enforced 64-revision family limit apply before eligibility; every cutoff collapse defensively probes `LIMIT 65` through `(source_key,revision_family_key,recorded_at DESC,revision_id)`. After collapse, order eligible rows by `publishedAt DESC NULLS LAST`, `collectedAt DESC`, `stableConnectorDocumentId ASC`, `revisionId ASC`; the first 1,000 are selected and every remaining eligible family is `deferred_due_scan_cap`. Thus one connector examines at most 1,000,000 registry keys and 64,000,000 retained revisions even when every row is future-knowledge, stale, revoked or otherwise ineligible; no post-filter output/page limit substitutes for either prefilter bound.

A request cannot add, group, remove or override a field. ## Revision payload and hashes

The authoritative revision columns are:

```text
revisionId, revisionFamilyKey, sourceKey, sourceIdentityAuthorityId, approvedSourceIdentityId, stableConnectorDocumentId,
canonicalUrlCandidate|null, publishedAt|null, collectedAt, recordedAt,
adapterVersion, acquisitionStatus, rawFieldPayload, rawCodePointCount,
rawFieldPayloadAlgorithmVersion, ingestionContentRevisionSha256|null,
canonicalContentAlgorithmVersion, ingestionCanonicalContentHashV3|null,
supersedesRevisionId|null
```

`acquisitionStatus` is exactly `complete|invalid_utf8|required_field_missing|content_overflow`. For `complete`, `rawFieldPayload` is the exact JSON array of ordered raw strings/segments, both hashes are non-null 64-character lowercase hex and `rawCodePointCount <= 100000`. Despite its retained wire name, `rawCodePointCount` is the count of the ordered field values after the exact per-field BOM removal, CRLF/CR-to-LF conversion and NFKC normalization owned by `entity-link-contract.md`; transcript timestamps and segment IDs do not contribute. The raw revision preimage still hashes the unmodified payload as RFC 8785 canonical JSON of `{"version":"raw-field-payload-v3.0","adapterVersion":adapterVersion,"fields":rawFieldPayload}`. The canonical hash preimage and normalization are exactly `entity-link-contract.md`.

Acquisition decodes and normalizes incrementally. Invalid UTF-8 or a missing required field stores the typed status, null payload/hashes and a zero-or-observed bounded normalized count. Observing normalized code point 100001 stores `content_overflow`, `rawCodePointCount=100001`, null payload/hashes and no later bytes; compatibility characters are therefore bounded after expansion, never before it. These terminal acquisition rows retain document accounting without storing truncated authoritative text. Source scan maps every non-`complete` revision to `parse_failure` with zero claims/mentions.

The dataset-manifest selected tuple is `[sourceKey,revisionFamilyKey,sourceIdentityAuthorityId,approvedSourceIdentityId,stableConnectorDocumentId,normalizedCanonicalUrlOrNull,publishedAtOrNull,collectedAt,recordedAt,adapterVersion,acquisitionStatus,rawFieldPayloadAlgorithmVersion,rawHashOrNull,canonicalContentAlgorithmVersion,canonicalHashOrNull,supersedesRevisionIdOrNull,revisionId]`. It never reads the legacy content hash in `source_raw_documents.metadata`.

The complete `source_dataset` native sections are executable here. `connector_roots` contains `[sourceKey,registeredFamilyCount,eligibleCount,sourceEligibleManifestHash]` for every attempted registry key, sorted ASCII `sourceKey`. `selected_revision_rows` first selects the exact first `selectedCount=min(1000,eligibleCount)` post-collapse tuples from each connector's newest-first `source_eligible` rows, then assigns dataset ordinals by registry `sourceKey`, ascending `effectiveAt=publishedAt||collectedAt`, normalized canonical document ID and the original source-eligible row ordinal. `connector_conservation` contains `[sourceKey,registeredFamilyCount,eligibleCount,selectedCount,deferredDueScanCap]` in ASCII `sourceKey` order and requires `0<=eligibleCount<=registeredFamilyCount<=1000000`, `eligibleCount=selectedCount+deferredDueScanCap`, `selectedCount<=1000`, and equality with the connector root header/count. An attempted connector has all three section entries even at zero; an unattempted registry key has none. Duplicate/missing connector entries, a non-registry key, a selected tuple absent from the bound newest-first selected population, a normalized URL/document-ID mismatch, or any count mismatch fails before `source_dataset` completion.

## Resumable eligible-manifest hashing

Post-collapse eligible metadata is ordered by `publishedAt DESC NULLS LAST`, `collectedAt DESC`, `stableConnectorDocumentId ASC`, `revisionId ASC`. Each native row payload is the exact dataset-manifest selected tuple above. It is stored as the `rows` section of one `source_eligible` manifest under `manifest-storage-contract.md`, with `sourceKey`, `sourceCutoff`, database-counted `registeredFamilyCount` and `eligibleCount` as header fields. `sourceEligibleManifestHash` is exactly that universal manifest's root hash; there is no separate source-specific page/root or monolithic array hash. The universal 2,000-row/768-KiB-page/3-MiB-bundle rule, row identity, first/last identities, root preimage, atomic page commit and first-missing-page resume apply unchanged, so different worker schedules cannot change the root.

Eligibility counting applies the `LIMIT 1000001` sentinel after family collapse and before page creation. Sentinel overflow fails before any page or successful connector accounting. Selected document parsing is sharded as exactly one immutable revision per `source_parse_batch` job in the canonical dataset ordinal order above; this reorders only the already selected newest at-most-1,000 population and does not change selection membership or the source-eligible root. The 100,000-code-point, 200-claim and 1,000-mention single-document limits plus the field-size proof in `job-graph-contract.md` guarantee the full canonical-plus-JSON output bundle fits the accepted-result envelope; a valid maximum never depends on implementation-selected multi-document packing. Sharding never changes claim or mention order within a document.
